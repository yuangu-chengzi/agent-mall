## 一、地基：工具层与通用契约

### waynboot-util

- 职责：全项目地基：常量/枚举/异常/工具类/R 统一返回/订单号生成
- 谁依赖它：几乎所有模块 | 它依赖：data-redis（OrderSnGenUtil 要 Redis，属反向依赖）
- 关键类：ReturnCodeEnum（错误码字典）+ BusinessException + GlobalExceptionHandler（异常三件套）、R（返回信封）、OrderSnGenUtil（时间戳+计数器）
- 我的疑问：① 5102 重复、50143 跳号 ② Lua 计数器超限行为（彩蛋）

### waynboot-common

- 职责：全项目公共基础设施——全局配置绑定、策略模式支付分发、异常处理、通用工具
- 谁依赖它：几乎所有模块 | 它依赖：waynboot-domain-api（继承 WaynConfig）、waynboot-util
- 关键类：
  WaynConfigProperties（配置绑定 Bean，借继承 + 实例 setter 将 yml 值写入父类 static 字段，实现"一次注入，全局静态读取"）、
  PayTypeContext（策略模式上下文，Spring 自动注入所有 PayTypeInterface 实现到 Map，按 payType 分发）、
  PayTypeInterface（支付策略接口，getType() 返回策略编号，pay() 执行支付）

- 我的疑问（策略模式）：
  ① 开闭原则对比：switch 方案加新支付方式要改核心 PaymentPrepareSupport（高风险），策略模式只需新增一个 @Component 实现类 + PayTypeEnum 加一行，旧代码零改动。
  ② Spring 自动注入魔法：构造函数参数 List<PayTypeInterface>，Spring 自动找到所有实现 Bean 打包注入，遍历塞进 Map<type, strategy>，启动时自动建好映射表。
  ③ Setter 为何不能 static：JavaBean Introspector 不扫描 static 方法，Spring 配置绑定依赖 JavaBean 规范发现属性，static setter 不在规范内。
  ④ MP Lambda 方法引用原理：Order::getPayType 不调用方法，MyBatis-Plus 用序列化 Lambda 反射出方法名 "getPayType" → 去 get → 首字母小写 → 转下划线 → 得到列名 "pay_type"，以此实现类型安全的 SQL 构建。

### base 包（BaseController.getPage + ORDER BY 白名单）

- 职责：BaseController 为所有 Controller 提供通用分页构造方法 `getPage()`，从 HTTP 请求参数自动提取分页+排序条件，构建 MyBatis-Plus 的 `Page<T>` 对象
- 谁依赖它：所有 Controller 继承 BaseController | 它依赖：ServletUtils、SqlUtil、MyBatis-Plus Page/OrderItem
- 关键类：BaseController

#### getPage() 执行流程

```
HTTP请求参数
  │
  ├─ pageNum=?  → 默认1
  ├─ pageSize=? → 默认10
  ├─ sortName=? → 排序字段（支持逗号多字段，如 "createTime,userName"）
  └─ sortOrder=?→ asc/desc
        │
        ▼
  SqlUtil.escapeOrderBySql() ── 白名单安检：只放行 [a-zA-Z0-9_ ,.]
        │                      非法字符直接抛异常，阻断后续
        ▼
  驼峰→下划线（正则 [A-Z] → _$0 → toLowerCase）
  例：createTime → create_time
        │
        ▼
  构建 OrderItem → addOrder → 返回 Page<T>
```

#### ORDER BY 为什么必须手动防注入

核心矛盾：**JDBC PreparedStatement 的 `?` 占位符只能替代"值"，不能替代"SQL 结构"（表名、列名、ORDER BY 字段）。**
- MyBatis `#{}` → 编译为 `?`，值会被加引号 → `ORDER BY 'create_time'` → 语法正确但排序失效（按常量排，所有行等值）
- MyBatis `${}` → 直接字符串拼接 → `ORDER BY create_time` → 正常，但可注入 `ORDER BY create_time; DROP TABLE user`
- 结论：ORDER BY 字段天生只能用 `${}`，所以必须**自己写白名单校验**弥补安全缺口

#### SqlUtil 两道防线

| 防线 | 机制 | 挡什么 |
|------|------|--------|
| ① 正则白名单 | `matches("[a-zA-Z0-9_\\ \\,\\.]+")` | 任何非字母数字的SQL关键字、特殊字符（;、'、(、-- 等）|
| ② 长度上限 | 超过 500 字符抛异常 | 超长恶意字符串 |

- 我的疑问：
  ① 为什么 `escapeOrderBySql` 叫"转义"却只是校验？因为它实际上不修改值——合法就原样返回，非法就抛异常。"escape"在这里是"防逃逸/防注入"的语义，不是字符转义。
  ② 为什么先判空 `isNotEmpty(value) && !isValid`？短路求值：空值跳过正则校验，避免 `null.matches()` 触发 NPE。
  ③ 为什么不直接用 MyBatis-Plus 的 `apply()` 方法拼接？MyBatis-Plus 的 `apply()` 本质还是字符串拼接，没有自动防注入能力，仍需手动白名单校验。

### waynboot-domain-api

### WaynConfig 跨模块设计
- 职责：WaynConfig（domain-api）定义静态配置载体 + 契约；WaynConfigProperties（common）作为 Spring Bean 在启动时将 yml 值通过实例 setter 写入父类 static 字段，实现"一次注入，全局静态读取"
- 谁依赖它：全项目静态调用 WaynConfig.getXxx() | 它依赖：common 依赖 domain-api（继承 WaynConfig）
- 关键类：WaynConfig（静态字段 + 实例 setter 桥接 static）、WaynConfigProperties（@Component 空子类，仅借继承触发属性绑定）

- 存有的问题：
  ① 静态状态 = 隐式全局变量：测试时无法直接设值，必须用 Field.setAccessible(true).set(null, val) 反射暴力写入；多测试并发时 static 字段被相互污染，结果不可靠。
  ② 初始化顺序敏感：static 字段由 WaynConfigProperties Bean 初始化时才填充，但 @PostConstruct、static{} 代码块、main 早期调用可能在这一刻之前执行，拿到 null，不抛异常，静默出错。
  ③ 继承语义被滥用：WaynConfigProperties extends WaynConfig 的真实意图不是"是一种"，而是借父类的 @ConfigurationProperties 声明和 setter 方法签名——用面向对象语法做技术 hack，读代码的人会被误导。
- 现代替代：普通 @ConfigurationProperties Bean + 构造函数注入，消除 static，测试友好，依赖明确，Spring 保证初始化顺序。

### mybatis-plus

### ① yml 全局声明生效链路（逻辑删除为例）

```yaml
# application.yml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: delFlag
      logic-delete-value: 1
      logic-not-delete-value: 0
```

#### 生效链路

```
Spring Boot 启动
  → MybatisPlusProperties Bean 读取 yml 的 mybatis-plus.* 配置
    ↑ 它自己就是一个 @ConfigurationProperties(prefix="mybatis-plus") Bean
  → MP 拿 db-config.logic-delete-field: delFlag 装配"全局逻辑删除规则"
  → 从此所有实体：
      - 字段名匹配 delFlag 的
      - 查询时自动追加 WHERE del_flag = 0
      - 删除时从 DELETE 改写为 UPDATE ... SET del_flag = 1
```

#### SQL 日志验证法

```yaml
# 开发环境打开 SQL 日志，验证逻辑删除是否生效
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
```

观察控制台：

```sql
-- 执行 orderMapper.deleteById(100) 后输出的实际 SQL：
UPDATE `order` SET del_flag = 1 WHERE id = 100 AND del_flag = 0
--                                     ↑ 自动追加         ↑ 逻辑删除而非物理删除

-- 执行 orderMapper.selectById(100) 后输出：

```

### ② 未知状态的防御三层

#### 为什么需要防御

`OrderStatusEnum.getDescByOrderStatus(42)` → 返回 `null`。如果这个 null 流到前端或 Excel 导出，可能直接 NPE 崩溃。三层防线让错误尽早暴露、优雅降级。

#### 第一层：入口防御（最有效）

未知数据进系统时就拦，不让脏数据落库。

```java
// MQ 消息、支付回调等外部数据入口
public void handleExternalOrderStatus(Short status) {
    Set<Short> validStatuses = Arrays.stream(OrderStatusEnum.values())
        .map(OrderStatusEnum::getStatus)
        .collect(Collectors.toSet());

    if (!validStatuses.contains(status)) {
        log.error("收到未知订单状态: {}", status);
        throw new BusinessException("非法的订单状态: " + status);
    }
    // 继续处理
}
```

数据库层兜底（如果能改库）：

```sql
ALTER TABLE `order` ADD CONSTRAINT chk_order_status
  CHECK (order_status IN (101,102,103,201,202,203,301,401,402));
```

#### 第二层：fail-fast（让错误尽早暴露）

当前写法（返回 null 的定时炸弹）：

```java
public static String getDescByOrderStatus(Short status) {
    for (...) { if (...) return desc; }
    return null;  // ← 调用方拿到 null，继续传，可能在 10 层调用后才炸
}
```

改进为"查不到就炸"：

```java
// requireByStatus：要么给值，要么炸
public static String requireByStatus(Short status) {
    for (OrderStatusEnum e : values()) {
        if (Objects.equals(e.getStatus(), status)) return e.getDesc();
    }
    throw new BusinessException("未知订单状态: " + status);
    //  ↑ 当场炸，不让 null 往下传播
}

// 或者返回 Optional（温和版，调用方必须处理）
public static Optional<String> getDescByStatus(Short status) {
    for (OrderStatusEnum e : values()) {
        if (Objects.equals(e.getStatus(), status)) return Optional.of(e.getDesc());
    }
    return Optional.empty();
}
```

#### 第三层：展示兜底

管理端界面即使漏了一个未知状态，也不能崩溃或白屏：

```java
public static String getDescOrUnknown(Short status) {
    return getDescByStatus(status).orElse("未知状态(" + status + ")");
}
// 效果：状态码 42 → 显示 "未知状态(42)"，而不是空白或 NPE 爆炸
```

#### 三层关系

```
外部数据 ──→ [第一层：入口拦截] ──→ 合法数据落库
                  │ 不合法的直接拒收 + 告警

代码内部 ──→ [第二层：fail-fast] ──→ 要么拿值，要么当场炸
                  │ 不让 null 偷偷传播

前端展示 ──→ [第三层：展示兜底] ──→ 显示 "未知状态(42)"
                  │ 防御任何漏网之鱼
```

### ③ 自动填充字段的三方案对比

三种方式都能实现 "创建时自动填 createTime/updateTime、创建人/更新人"：

#### 对比表

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **手动 set** | 每个 Service 里写 `order.setCreateTime(now)` | 代码显式，调试时一眼看到赋值 | 散落各处，容易遗漏；新人加新表不知道要填 |
| **DB 默认值** | `DEFAULT CURRENT_TIMESTAMP` | 绝对防漏；绕过应用修改也生效 | 只对时间有效，创建人/更新人做不到；业务逻辑藏在 DDL 里 |
| **MetaObjectHandler** | `@Component` 实现 `MetaObjectHandler` 接口 | 全局统一，一次配置全表生效；支持时间+操作人 | 隐形魔法，调试时难追踪；多线程场景要注意 ThreadLocal 传值 |

#### MetaObjectHandler 实现

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {
    @Override
    public void insertFill(MetaObject metaObject) {
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "createBy", String.class, getCurrentUser());
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
        this.strictUpdateFill(metaObject, "updateBy", String.class, getCurrentUser());
    }
}
```

实体字段上标记：

```java
@TableField(fill = FieldFill.INSERT)       // 插入时自动填充
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE) // 插入和更新时都填充
private LocalDateTime updateTime;
```

#### MetaObjectHandler 的代价

| 代价 | 说明 |
|------|------|
| 隐形魔法 | 字段值不是代码里赋的，调试时看 Service 找不到赋值语句，新人一头雾水 |
| 字段名硬编码 | `"createTime"` 是字符串，字段重命名编译不报错，运行时静默失效 |
| ThreadLocal 依赖 | 取当前用户靠 `SecurityUtils.getCurrentUser()`，本质是 ThreadLocal，异步/多线程场景容易拿不到 |
| 误伤风险 | 全表全局生效，有些表不需要自动填充的字段如果同名也会被覆盖 |
| SQL 日志不变 | 日志里看不到这些赋值，排查数据问题困难 |

#### 一句话总结

> 小项目手动 set 足够；中大型项目 MetaObjectHandler 省心但要理解其隐形代价；DB 默认值做时间兜底是最稳的。三者不互斥，可以组合用（MetaObjectHandler 管人 + DB 默认值管时间）。

## 二、基础设施：Redis 与 Elasticsearch

### waynboot-data-redis

### 序列化三件套

`CacheConfig.redisTemplate()` 自定义了四种序列化器，分两类：

| 位置 | 用谁 | 为什么 |
|------|------|--------|
| **Key** | `StringRedisSerializer` | key 必须是明文字符串，方便 `redis-cli KEYS *` 查找和调试 |
| **HashKey** | `StringRedisSerializer` | 同上，hash 的 field 也要可读 |
| **Value** | `GenericFastJsonRedisSerializer` | 对象自动转 JSON，存进去是人看的，不挑语言 |
| **HashValue** | `GenericFastJsonRedisSerializer` | 同上 |

**选型关键：为什么不用 JDK 默认序列化？**

Spring Boot 自动配置的 `RedisTemplate` 默认用 `JdkSerializationRedisSerializer`：

```
存进去：\xAC\xED\x00\x05t\x00\x04user1    ← 不可读二进制
自定义：{"name":"张三","age":20}           ← JSON
```

后果：用 `redis-cli` 查数据全是乱码，排查问题靠猜。而且 JDK 序列化要求类实现 `Serializable`，跨语言（Go/Python 读 Redis）不可能。

**为什么不用 Jackson 而用 FastJSON？**

项目已经在用 FastJSON（`BaseController.toJson()` 也是 FastJSON），保持依赖一致。功能上两者等价。

### Key 设计哲学：前缀 + TTL 绑定

#### 模板

```java
@Getter
public enum RedisKeyEnum {
    CAPTCHA_KEY_CACHE(CacheConstants.CACHE_PREFIX + "captcha_key:", 300),
    GOODS_DETAIL_CACHE(CacheConstants.CACHE_PREFIX + "goods_detail:", 300),
    ORDER_RESULT_KEY(CacheConstants.CACHE_PREFIX + "order_result_key:", 60),
    ;
    private String key;          // 前缀模板，如 "wayn:captcha_key:"
    private Integer expireSecond; // TTL（秒）
}
```

拼接使用：`RedisKeyEnum.CAPTCHA_KEY_CACHE.getKey(uuid)` → `"wayn:captcha_key:abc123"`

#### 三层设计

| 层 | 示例 | 作用 |
|----|------|------|
| **全局前缀** | `CacheConstants.CACHE_PREFIX`（`wayn:`） | 避免多项目共用 Redis 时 key 冲突；`KEYS wayn:*` 一键定位本项目所有 key |
| **业务标识** | `captcha_key` / `order_result_key` | 一眼看出谁在用 |
| **动态后缀** | `:uuid` / `:orderSn` | 区分不同实例 |

#### 为什么 key 以 `:` 结尾？

`:` 是 Redis 推荐的命名分隔符，在可视化工具（RDM/RedisInsight）中会自动折叠成树形：

```
wayn:
  ├─ captcha_key:
  │    ├─ abc123
  │    └─ def456
  ├─ goods_detail:
  │    └─ 1
  └─ order_result_key:
       └─ SN20240101
```

比用 `_` 或 `-` 直观得多。

### 为什么 key 模板和 TTL 绑在一起是神来之笔

**Redis 内存泄漏的第一大原因：设了 key，忘了设过期。**

#### 传统写法（散落式）

```java
// A同事
redis.set("wayn:captcha_key:abc", code);              // 忘了设 TTL → 永不过期
// B同事
redis.set("wayn:captcha_key:def", code, 300, SECONDS); // 设了300秒
// C同事
redis.set("wayn:captcha_key:ghi", code, 120, SECONDS); // 设了120秒 → 不一致
```

三个问题同时出现：**漏设 TTL、TTL 不一致、散落各处没法统一改。**

#### 枚举式（绑定式）

```java
redisTemplate.opsForValue().set(
    RedisKeyEnum.CAPTCHA_KEY_CACHE.getKey(uuid),  // key
    code,
    RedisKeyEnum.CAPTCHA_KEY_CACHE.getExpireSecond(),  // TTL — 编译期强制绑定
    TimeUnit.SECONDS
);
```

| 优势 | 说明 |
|------|------|
| **编译期强制** | 构造方法要求传 TTL，不想写也得写 |
| **统一口径** | 同一个 key 模板，全项目同一个 TTL，不会出现 A 设 300、B 设 120 |
| **改一处生效** | 想调整 TTL，改枚举一个数字即可 |
| **代码即文档** | 一眼看到所有 key 和对应的过期策略 |

#### 真实事故对照

```
事故：Redis 内存持续上涨，最终 OOM
排查：redis-cli --scan | while read k; do ttl=$(redis-cli TTL "$k"); done
发现：300+ 个 key TTL=-1（永不过期）
根因：团队没有强制 TTL 机制，开发者经常忘记设过期
修复：全部收拢到 RedisKeyEnum + 给所有枚举加 TTL + 代码审查检查是否用了裸 redis.set()
```

### Lua 脚本专栏

项目内 `RedisCache` 承载了 5 段 Lua 脚本，全部通过 `DefaultRedisScript + redisTemplate.execute` 在 Redis 服务端原子执行。本节覆盖四段核心业务脚本（第五段 `buildLuaTokenBucketScript` 另见令牌桶专题）。

#### 5 段脚本一览表

| 脚本 | 类名/Method | KEYS | 核心动作 | 返回值语义 | 对应业务 |
|------|-----------|------|---------|-----------|---------|
| 库存预占 | `buildLuaReserveStockScript` | availableKey, reservedKey, orderKey | `incrby reserved, set orderKey` | 1=成功/-1=不足/-2=未初始化/-3=非法 | 普通下单 |
| 预占释放 | `buildLuaReleaseReservedStockScript` | reservedKey, orderKey | `decrby reserved, del orderKey` | 1=成功/0=幂等（已释放） | 普通下单 finally |
| 秒杀抢购 | `buildLuaAcquireSeckillStockScript` | stockKey, userKey, tokenKey, resultKey | `decrby stock, set userKey, set resultKey` | 1=成功/-1=不足/-2=未初始化/-3=重复/-4=token非法/-6=参数 | 秒杀 |
| 令牌桶 | `buildLuaTokenBucketScript` | key（Hash） | `hmget, 计算补充, hmset` | 1=放行/0=限流/-1=参数 | 秒杀限流 |

#### 三把 key 的预扣设计（库存预占核心）

```
┌─────────────────────────────────────────────────┐
│  availableKey：库存快照（从 MySQL 同步来的常量）    │
│  reservedKey：在途计数器（正在办业务的人数）        │
│  orderKey：订单号条（这个订单占了多少）              │
├─────────────────────────────────────────────────┤
│  Lua 判断：available - reserved >= request？      │
│  放行：reserved +N, orderKey SET N               │
│  release：reserved -N（从 orderKey 取值）,       │
│          orderKey DEL                            │
└─────────────────────────────────────────────────┘
```

##### 为什么是 `available - reserved` 而不是只看 `available`？

`available` 是**静态快照**（定时任务从 MySQL 同步），请求通过后不修改。如果只看 `available`，每个并发请求都读到同一个数，全部判定"够"，全部放行 → 超卖。

`reserved` 是**动态痕迹**。每个通过的请求做 `incrby reserved`，后面的请求来检查时，`available - reserved` 的差值会越来越小。Lua 原子性保证"读 + 算 + 写"中间不被插队。

##### reservedKey 为什么每次请求都刷新 TTL？

因为 reservedKey 是**共享计数器**。只要还有人"在路上"（拿到闸门许可但还没完成 MySQL 落库），计数器就不能过期消失。每次新的预占请求 `expire` 一下重新倒计时 30 秒。最后一个请求离去 30 秒后，自动清理。

##### orderKey 为什么一次性 SET EX 30 后永不刷新？

orderKey 是**订单级别的独立 key**。代表"某一个人某一次操作"。30 秒足够完成 MySQL 落库 + finally release。如果超时说明这个请求已经凉了，它就应该过期消失——不需要别人替它续命。

##### 释放时为什么从 orderKey 取值而不是从调用方传数？

```lua
local reservedNumber = redis.call('get', orderKey)   -- 取当时预占的数量
redis.call('decrby', reservedKey, tonumber(reservedNumber))
```

调用方可能传错数量，或者 release 被重复调用。从 orderKey 取值保证 **"释放的数量一定等于预占时的数量"**，不会多还也不会少还。

#### 幂等模式

三段"拿资源"的脚本各自实现了不同粒度的幂等：

| 脚本 | 幂等 Key | 机制 | 场景 |
|------|---------|------|------|
| `luaReserveStock` | `orderKey` | `exists(orderKey) == 1 → return 1` | 同一订单别重复预占 |
| `luaReleaseReservedStock` | `orderKey` | `get(orderKey) == nil → return 0` | 释放过就别再减了 |
| `luaAcquireSeckillStock` | `userKey` | `exists(userKey) == 1 → return -3` | 每人每个 SKU 只能抢一次 |

前两个是**订单维度**幂等（一个订单的预占/释放只能做一次），第三个是**用户维度**去重（一个人不能重复抢同一个商品）。粒度不同，目的不同。

#### KEYS vs ARGV

```
KEYS：脚本里要读写的 Redis key 名字    → 用于 Redis Cluster 路由
ARGV：纯业务参数（数字、token、TTL）   → 不参与路由
```

在 Redis Cluster 下，脚本执行前会根据 KEYS 中的 key 定位到正确节点。如果 KEYS 中的 key 分布在多个节点，脚本直接拒绝执行。要兼容 Cluster，同一脚本的 KEYS 必须用 Hash Tag `{productId}` 保证落在同一个 slot。

#### Redis 版本兼容笔记

在 Redis 3.2 ~ 4.x 时代，主从复制通过重放整个 Lua 脚本实现。非确定性命令（如 `TIME`）在同一脚本的不同执行节点上返回值不同，会导致主从数据不一致。因此 Redis 强制：`TIME` 之后禁止写命令。Redis 5 引入 **effect replication**（直接复制写命令而非重放脚本），该限制放开。令牌桶脚本中的 `redis.call('time')` + `hmset` 在这种历史背景下才成立。

### RedisLock 分布式锁

`RedisLock` 位于 `com.wayn.data.redis.manager`，是三段 Lua 脚本驱动的可重入分布式锁，配合 watch-dog 自动续期。

#### 三要素表

分布式锁的三条金科玉律：

| 要素 | 含义 | 本项目实现 | 对应位置 |
|------|------|-----------|---------|
| **互斥** | 同一时刻只有一个人拿锁 | `SETNX`：key 不存在才能 SET 成功，否则返回 0 | `buildLuaLockScript` |
| **防死锁** | 拿了锁的人挂了，锁不能永远卡着 | `EXPIRE`：加锁成功后立即设过期时间 + watch-dog 后台续期 | `buildLuaLockScript` + `buildLuaRenewScript` |
| **防误删** | 不能把别人的锁删了 | 解锁前 `GET key == nanoId` 身份校验，是自己的才 `DEL` | `buildLuaUnLockScript` |

三条规则缺一不可。缺互斥 → 并发冲突；缺防死锁 → 服务挂了 key 永不过期，全系统瘫痪；缺防误删 → A 业务跑太久锁过期，B 拿到锁，A 回来把 B 的锁删了。

#### 三段 Lua 脚本

##### 加锁脚本 `buildLuaLockScript`

```lua
local key = KEYS[1]
local value = ARGV[1]          -- nanoId（线程唯一标识）
local time_out = ARGV[2]        -- 超时时间

local result = redis.call('get', key)
if result == value then
    return 1;                   -- 可重入：已经是我的锁，直接成功
end
local lock_result = redis.call('setnx', key, value)
if tonumber(lock_result) == 1 then
    redis.call('expire', key, time_out)
    return 1;                   -- 首次加锁成功
else
    return 0;                   -- 锁被别人持有
end
```

逻辑：先查是不是自己的（可重入），不是再 `SETNX` 抢锁。`SETNX` + `EXPIRE` 放在一个 Lua 脚本里，原子性杜绝"SETNX 成功、EXPIRE 失败 → 死锁"这种经典竞态。

##### 解锁脚本 `buildLuaUnLockScript`

```lua
local key = KEYS[1]
local value = ARGV[1]
local result = redis.call('get', key)
if result ~= value then
    return 0;                   -- 不是我的锁，不删
else
    redis.call('del', key)
end
return 1;
```

先验证身份再删。如果省掉这一步直接 `DEL`，锁过期后被别人拿走后，你的 finally 会把别人的锁误删。

##### 续期脚本 `buildLuaRenewScript`

```lua
local key = KEYS[1]
local value = ARGV[1]
local timeout = ARGV[2]
local result = redis.call('get', key)
if result ~= value then
    return 2;                   -- 锁已丢失，通知 Java 关闭看门狗
end
local ttl = redis.call('ttl', key)
if tonumber(ttl) < tonumber(timeout) / 2 then
    redis.call('expire', key, timeout)
    return 1;                   -- 续期成功
else
    return 0;                   -- TTL 还充足，无需续期
end
```

三条返回值分支：

| 返回值 | 含义 | Java 侧行为 |
|--------|------|-----------|
| `1` | TTL 不足一半，执行了续期 | 继续看门狗周期 |
| `0` | TTL 还充足，跳过 | 继续看门狗周期 |
| `2` | 锁已不属于自己 | **关闭看门狗线程** |

#### 看门狗机制

`lock()` 加锁成功后，启动一个 `ScheduledExecutorService`，每 `timeout/3` 毫秒执行一次续期脚本：

```java
scheduledExecutorService.scheduleWithFixedDelay(() -> {
    Long result = (Long) redisTemplate.execute(renewRedisScript, ...);
    if (result != null && result == 2) {
        ThreadUtil.shutdownAndAwaitTermination(scheduledExecutorService);  // 锁丢了，关闭
    }
}, timeoutTmp / 3, timeoutTmp / 3, TimeUnit.MILLISECONDS);
```

**续期阈值：TTL < timeout/2 才续。** 不是每次触发都无脑 `EXPIRE`，减少不必要的 Redis 写操作。

**看门狗生命周期：**

```
lock() 成功 → 创建看门狗线程
  │
  ├─ (等待 timeout/3)
  ├─ 执行续期检查 → TTL < timeout/2 ? EXPIRE : 跳过
  ├─ (等待 timeout/3)
  ├─ 执行续期检查 → ...
  └─ 停止条件：
       ├─ unLock() 主动释放 → shutdown
       └─ 续期返回 2（锁丢失） → shutdown
```

#### 可重入技巧与缺陷

`ThreadLocal<String>` 给每个线程分配唯一的 `nanoId`，加锁脚本中 `if result == value then return 1` 实现可重入——同一线程拿同一把锁不会阻塞。

**但这是一个"半可重入"实现，有两个缺陷：**

**缺陷一：没有计数器，一次 unlock 全部释放**

```java
lock("order:123");    // 第 1 次
  lock("order:123");  // 第 2 次（可重入成功）
  unLock("order:123"); // 直接 DEL！第 1 次加的锁也丢了
// 外层还在跑，但锁没了
```

正确做法应该用 Redis Hash 存 `{nanoId: count}`，`lock` 时 `HINCRBY`，`unlock` 时 `HINCRBY -1`，count 归零才 `DEL`。

**缺陷二：重复加锁导致看门狗线程泄漏**

每次 `lock()` 成功都 `new ScheduledExecutorService()` 并覆盖 `ThreadLocal`：

```
第 1 次 lock：创建 WatchDog-A → executorServiceThreadLocal 指向 A
第 2 次 lock：创建 WatchDog-B → executorServiceThreadLocal 指向 B（A 引用丢失！）

WatchDog-A：没了引用，但非守护线程仍在运行，永远关不掉
```

修复思路：可重入时 `flag == true` 但应跳过看门狗创建，因为第一次就已经启动了。

#### ⚠️ 时间单位 Bug

这是本模块最隐蔽的缺陷。

```java
// RedisLock.java
public static final Integer DEFAULT_TIME_OUT = 30;   // 注释："默认锁过期时间 30 秒"
timeoutTmp = DEFAULT_TIME_OUT * 1000;                 // → 30000
```

开发者的意图是把秒转成毫秒：30 秒 × 1000 = 30000 毫秒。但 Lua 脚本用的是 `EXPIRE`：

```lua
redis.call('expire', key, time_out)   -- EXPIRE 单位是 秒
```

**计算结果：**

```
传入值 30000 → EXPIRE(key, 30000) → TTL = 30000 秒 = 500 分钟 ≈ 8.3 小时

注释声称：30 秒
实际效果：8.3 小时
偏差：1000 倍
```

修复方式二选一：

| 方案 | 改哪里 | 做法 |
|------|--------|------|
| A | Java 侧 | `timeoutTmp = DEFAULT_TIME_OUT`（去掉 * 1000） |
| B | Lua 侧 | `redis.call('pexpire', key, time_out)`（用毫秒） |

**连带影响：**

- 自定义 timeout 参数（单位"分钟"）也受影响：`timeout * 1000` 秒，而不是分钟
- 看门狗续期同样用 `EXPIRE`，传入 30000 → 续 30000 秒，看门狗几乎永远不需要续
- 看门狗调度周期 `30000/3 = 10000` 毫秒（10 秒），但 TTL 是 30000 秒，续期阈值 `15000` 秒，触发概率极低

### MyRedisCacheManager：`#TTL` 动态缓存时间

`MyRedisCacheManager extends RedisCacheManager`，重写 `createRedisCache` 实现通过缓存名内嵌 TTL：

```java
@Override
protected RedisCache createRedisCache(String name, RedisCacheConfiguration cacheConfig) {
    String[] array = StringUtils.split(name, "#");
    name = array[0];
    if (array.length > 1) {
        long ttl = Long.parseLong(array[1]);
        cacheConfig = cacheConfig.entryTtl(Duration.ofSeconds(ttl));
    }
    return super.createRedisCache(name, cacheConfig);
}
```

**约定：`@Cacheable(value = "cacheName#TTL秒")`**

```java
@Cacheable(value = "category_index_cache#300")    // TTL 300 秒 = 5 分钟
@Cacheable(value = "bannerCache")                  // 未设 → 走全局默认 TTL
```

把 TTL 从配置文件或全局默认中解放出来，让每个缓存在注解里就地声明过期时间，**就近原则**：看注解就知道这个缓存多久过期，不用翻配置类。

`MyRedisCacheManager` 这里正确使用了 `Duration.ofSeconds(ttl)`，注释还特意标"注意单位我此处用的是秒，而非毫秒"——与 `RedisLock` 的 `EXPIRE` Bug 形成鲜明对比。

### ShedLock：定时任务分布式互斥

#### 解决的问题

admin 多实例部署时，`@Scheduled` 定时任务每个实例都会触发——导致同一任务重复执行 N 次：

```
实例 A：凌晨 2:00 执行库存对账
实例 B：凌晨 2:00 执行库存对账  ← 重复！
实例 C：凌晨 2:00 执行库存对账  ← 重复！
```

#### 三层配置

**1. 依赖：** `shedlock-spring` + `shedlock-provider-redis-spring`

**2. Bean 配置（ShedLockConfig，3 行）：**

```java
@Bean
public LockProvider lockProvider(RedisConnectionFactory connectionFactory) {
    return new RedisLockProvider(connectionFactory, "waynboot-mall");
}
```

`"waynboot-mall"` 是 Redis Key 前缀，所有 ShedLock 锁统一以 `waynboot-mall:` 开头。

**3. 注解使用：**

```java
@Scheduled(cron = "0 */5 * * * *")
@SchedulerLock(name = "tradeStockSnapshotRefreshJob",
               lockAtMostFor = "PT4M",    // ISO-8601：最多 4 分钟
               lockAtLeastFor = "PT30S")   // 最少 30 秒
public void refreshStockSnapshot() { ... }
```

#### 三个参数语义

| 参数 | 作用 | 为什么需要 |
|------|------|-----------|
| `name` | 锁的唯一标识，同一 name 的所有实例互斥 | 不同任务用不同 name，否则互相阻塞 |
| `lockAtMostFor` | 最长持锁时间，到期自动释放 | 防止持锁节点崩溃后锁永远不释放、任务永久卡死 |
| `lockAtLeastFor` | 最短持锁时间，即使任务秒级完成也不释放 | 防止时钟漂移导致两个节点几乎同时执行 |

#### ShedLock vs RedisLock（手写）

| 维度 | ShedLock | RedisLock（手写） |
|------|----------|-------------------|
| **适用场景** | 定时任务（`@Scheduled` 方法） | 用户操作、业务流程 |
| **加锁方式** | 一个注解 | 手动 `lock()` / `unLock()` |
| **释放方式** | 自动（任务结束或超时） | 手动 `finally { unLock() }` |
| **动态 Key** | 不支持 | 支持 `lock("order:"+id)` |
| **嵌套加锁** | 不支持 | 部分支持（可重入，但有 Bug） |

**定位：ShedLock 只管定时任务互斥，用户触发的方法还是得手写锁。** 两者不互斥，各管各的场景。

#### 当前项目 ShedLock 使用清单

所有加锁任务在 `TradeGovernanceScheduledTask`：

| 任务 | name | 频率 | lockAtMostFor |
|------|------|------|--------------|
| 库存快照刷新 | `tradeStockSnapshotRefreshJob` | 每 5 分钟 | PT4M |
| 库存对账 | `tradeInventoryReconcileJob` | 每小时 | PT30M |
| 支付日终对账 | `tradePaymentDailyReconcileJob` | 每天 2 点 | PT1H |

另有一个 `LocalMessageRelayTask` 有 `@Scheduled` 但无 `@SchedulerLock`——它在 `waynboot-domain-trade` 模块，不跑在 admin 实例上，不需要互斥。

### 倒排索引 vs MySQL B+Tree（概念核心）

#### 一句话对比

| | ES 倒排索引 | MySQL B+Tree |
|------|------------|-------------|
| **索引单元** | 词条（Term），对文本分词后建立 | 字段原始值（整数、字符串前缀） |
| **检索方向** | 从"词"找"文档"（反向映射） | 从"键值"找"行"（正向查找） |
| **核心结构** | Term Dictionary → Posting List | 多层 B+Tree，叶子节点有序且互联 |
| **查询复杂度** | 词典 O(1) + 遍历倒排链 | B+Tree 查找 O(log n) |
| **适用场景** | 全文检索、模糊匹配、相关性排序 | 精确匹配、范围查询、排序 |

#### 为什么 MySQL LIKE '%手机%' 又慢又不准？

三个根本原因：

**① 扫描方式：必须全表扫描。** `LIKE '%keyword%'` 以 `%` 开头，B+Tree 的前缀有序性完全失效，索引不走，每一行都得读出来做字符串匹配。10 万条商品 = 10 万次字符串比较。

**② 分词能力：没有分词概念，只有逐字符子串匹配。** "手机壳"不等于"壳手机"（LIKE '%手机%' 第一个命中第二个不命中），也不等于"手 机"（中间有空格就不匹配）、"shouji"（拼音完全不认）。ES 用 IK 分词器把"手机壳"拆成 `["手机","壳"]`，搜索"手机"就能命中。

**③ 排序能力：没有相关性概念。** LIKE 结果只能按某个字段值排序（id、时间），排第一的不等于最相关。ES 用 BM25 算法：词频（TF）+ 逆文档频率（IDF）+ 字段长度归一化，真正按"搜什么给什么"来排。

#### 倒排索引怎么建？

```
原始文档：
  文档1 → "苹果手机很好用"
  文档2 → "苹果很好吃"
             │
             ▼  IK 分词器（ik_max_word）
  文档1 → ["苹果", "手机", "很", "好用"]
  文档2 → ["苹果", "很", "好吃"]
             │
             ▼  建倒排链
  "苹果" → [doc1, doc2]
  "手机" → [doc1]
  "好用" → [doc1]
  "好吃" → [doc2]
  "很"   → [doc1, doc2]

搜索 "手机"：O(1) 查词典 → 倒排链 [doc1] → 返回文档1
```

### 分词：项目用了什么分析器？

#### goods 索引 Mapping（es/index/goods.json）

| 字段 | 类型 | 分析器 | 用途 |
|------|------|--------|------|
| `name` | `text` | `ik_max_word`（最细粒度分词） | 主搜索字段，搜"手机"能命中"苹果手机壳" |
| `name.kw` | `completion` | `keyword`（不分词，原样存） | 搜索自动补全（Suggester），输入"苹"补全"苹果" |
| `name.py` | `completion` | `pinyin` | 拼音搜索 + 拼音补全，输入"shouji"搜出"手机" |
| `pyname` | `text` | `pinyin` | 商品名拼音全量索引，按拼音 match 查询 |
| `keyword` | `keyword` | 不分词 | 精确匹配，如 `keyword: "新品"` |
| `retailPrice` | `float` | —（数值型不走分词） | 范围过滤/排序，靠 doc_values |
| `sales` | `integer` | — | 排序字段 |
| `isOnSale` | `boolean` | — | 过滤上下架 |

#### 三种分析器实际效果演示

```
输入："苹果手机iPhone15"

ik_max_word：["苹果", "手机", "iPhone", "15", "苹", "果", "机"]
keyword：    ["苹果手机iPhone15"]   ← 一整坨，只有当精确匹配时用
pinyin：     ["pingguo", "shouji", "iPhone15", "pg", "sj"]
```

#### ik_max_word vs ik_smart

- `ik_max_word`：最细粒度，"苹果手机" → `["苹果", "手机", "苹果手机"]`，召回率最高，但索引体积大
- `ik_smart`：粗粒度，"苹果手机" → `["苹果手机"]`，更精准但可能漏召回
- 本项目选 `ik_max_word`：电商搜索第一要务是"别漏"（宁多勿缺）

#### 自定义词典

`es/plugins/ik/config/` 下的 `.dic` 文件就是 IK 分词器的扩展词库：
- `extra_main.dic`：业务专有词（品牌名、型号、黑话），确保 IK 能正确切分
- `extra_stopword.dic`：停用词（了、的、呢），索引时不建倒排链，节省空间

#### 为什么 ElasticEntity 是 Map 而不是强类型 POJO？

```java
// ❌ 如果强类型，新增一个字段就要改 Java 类 + 重新编译部署
public class GoodsDoc {
    private Long id;
    private String name;
    private BigDecimal price;
    // ... 加一个字段要改这里
}

// ✅ Map 方案，新增字段只需改 buildGoodsElasticEntity() 里 put 一行
map.put("newField", goods.getNewField());
```

这是"搜索索引 Schema 频繁变化"场景下的务实选择。ES 的 Mapping 通过 `goods.json` 动态配置，Java 侧用 Map 对接，两边解耦——调整搜索字段不一定要改 Java POJO。

#### 全量同步的 Redis 锁

```java
redisLock.lock(RedisKeyEnum.ES_SYNC_CACHE.getKey(), 2);
```

锁实现位于 `RedisLock`，带有看门狗续期机制。注意一个已知 bug：Javadoc 写着 timeout 单位是"分钟"，但代码做的是 `timeout * 1000`，而 Redis EXPIRE 单位是秒。所以 `lock(key, 2)` 实际 TTL = `2 × 1000 = 2000 秒 ≈ 33 分钟`，严重偏长。更致命的是一直在续期，只要 JVM 不崩，锁永远不会自动过期。详见 `waynboot-data-redis.md` 的 RedisLock 章节。

### 一致性模型："副本可以有延迟，真相不能有"

#### 原则

```
MySQL  = 唯一真相源（Source of Truth）—— 下单、扣库存、价格校验永远走 MySQL
ES     = 只读搜索副本 —— 允许短暂不一致（最终一致性）
Redis  = 热点缓存副本 —— 允许短暂不一致，读取时重建
```

#### 价格不一致场景及应对

```
商品改了价格
  │
  ├─ MySQL 更新成功 ✅  ← 真相源
  ├─ Es 同步失败 ❌     ← 搜索副本（挂了）
  └─ Redis 缓存被清 ✅  ← 热点副本（已清除）
        │
        ▼
  用户搜索 "手机" → ES 返回旧价格（$999）
  用户点进详情页 → 查 MySQL → 看到新价格（$899）
  用户下单 → 下单接口验价走 MySQL → 用新价格创建订单
```

**只要下单验价走 MySQL，这个场景就不是 bug——它是最终一致性架构的正常运作。**

#### 三段式校验（从搜索到交易）

| 环节 | 数据源 | 一致性要求 | 出错了会怎样 |
|------|--------|-----------|-------------|
| **搜索列表** | ES | 最终一致（秒~分钟级延迟） | 看到旧价格/旧库存，但用户还没下单 |
| **商品详情** | MySQL（查详情 API） | 实时 | 用户做决策前看到真实数据 |
| **下单验价** | MySQL（`SELECT ... FOR UPDATE`） | 强一致 + 行锁 | 这是最后防线，绝不能出错 |

#### 为什么不用 ES 做下单校验？

倒排索引的核心价值是"搜得快"，不是"算得准"。ES 的近实时（Near Real-Time = 1 秒 refresh）在交易场景就是"有 1 秒窗口拿旧数据"，这 1 秒足够出现超卖。

#### MySQL → ES 同步三件套最佳实践

1. **全量同步（syncGoodsToEs）：** 兜底——定时任务每日凌晨跑一次，保证即使增量丢了，第二天也能自动修复
2. **增量同步（syncGoods2Es）：** 实时——商品 CRUD 后立刻同步单条，99% 的场景下保证 < 1 秒延迟
3. **监听 Binlog（未实现，进阶方案）：** 终极——Canal/Debezium 监听 MySQL binlog，做到秒级异步同步，比业务代码里写 `syncGoods2Es()` 更可靠，不会漏也不会忘

#### 真理法则

> **副本（ES/Redis）可以有延迟，真相（MySQL）不能有。ES 负责"搜得快"，MySQL 负责"算得对"。交易永远走真相。**

#### 为什么 CartServiceImpl 是纯委托？

这是 GoodsServiceImpl 同一个模式：**外观层不做业务决策，只做路由**。好处：

- 单元测试直接测 WriteSupport / ReadSupport，不需要构造完整的 ServiceImpl
- 切换存储（比如购物车从 MySQL 迁到 Redis）只需改 Support，Contract 和 Facade 不动
- 符合"组合优于继承"——Support 之间可以互相注入，ServiceImpl 只管串联

### 写路径加锁

购物车所有写操作（add / changeNum / updateChecked）都在用户维度加锁。锁 Key 为 `RedisKeyEnum.CART_LOCK.getKey(userId)`，超时 2 分钟。

#### 为什么是用户维度而不是购物车行维度？

行维度锁（`lock(cartId)`）的问题是：用户在手机上快速点两下"加入购物车"，两下是不同的 cartId（还没插入），行锁根本防不住。

用户维度锁保证：**同一个人的所有购物车写操作串行化。**

### 校验集中

CartValidationSupport 把购物车涉及的 5 种校验全部集中在一个类里：

| 校验方法 | 什么时候调 | 校验内容 | 失败抛什么 |
|----------|-----------|---------|-----------|
| `validateRequest` | 所有写操作入口 | goodsId/productId/number 非空且 >0 | PARAMETER_TYPE_ERROR |
| `requireOnSaleGoods` | 加购 | 商品存在 + isOnSale=true | PARAMETER_TYPE_ERROR / GOODS_HAS_OFFSHELF |
| `requireProduct` | 加购/改数量/默认货品 | 货品存在 + 归属校验 | GOODS_STOCK_NOT_ENOUGH |
| `ensureEnoughStock` | 加购/改数量 | 目标数量 ≤ 货品库存 | GOODS_STOCK_NOT_ENOUGH |
| `resolveDefaultProduct` | 无规格快加 | 商品有货品 + 优先取默认 | PARAMETER_TYPE_ERROR |

#### requireProduct 的货品归属校验

```java
GoodsProduct product = goodsProductService.getById(productId);
if (product == null || !Objects.equals(product.getGoodsId(), goodsId)) {
    throw new BusinessException(...);
}
```

这是**货品和商品交叉校验**——防止请求篡改 goodsId（传 iPhone 15 Pro Max 的 goodsId，但用 iPhone 15 Pro 的 productId），详见 Goods 和 Product 的关系。

### 读路径的失效自动修正

CartReadSupport 有两个方法做了"读写混合"：**读到失效数据时，顺手修一把。**

#### list() —— 列表展示时的库存修正

```java
// 查购物车列表 → 批量查对应货品库存
Map<Long, GoodsProduct> productMap = goodsProductService.selectProductByIds(productIdList);

for (Cart cart : cartList) {
    GoodsProduct product = productMap.get(cart.getProductId());
    if (product == null) {
        uncheckedCartIds.add(cart.getId());  // 货品都不存在了
        continue;
    }
    if (product.getNumber() < cart.getNumber()) {
        responseVO.setChecked(false);
        uncheckedCartIds.add(cart.getId());  // 库存不够了
    }
}
// 批量置为未勾选
cartMapper.update(null, Wrappers.lambdaUpdate(Cart.class)
        .set(Cart::getChecked, false)
        .in(Cart::getId, uncheckedCartIds));
```

**效果：用户打开购物车时，如果某商品已下架或库存不足，自动取消勾选，不会进到下个页面才发现买不了。**

#### getCheckedGoods() —— 结算时的双重过滤

进入结算页时同样做一次过滤：货品不存在或库存不足的购物车项标为未勾选，只把真正能买的商品汇总成结算信息。

#### 为什么不在写的时候就禁止？

写入时（加购）的校验是"当时够"，不代表"现在够"——可能加购后被人买光了。读路径的修正是一种**最终检查**，两段式校验：

```
写入时 → 校验（快照时刻：当时够就行）
读取时 → 修正（结算时刻：现在够才行）
```

### 三个观察

#### 观察一：快照 —— 为什么冗余 goodsName/price/picUrl？

fillCartSnapshot 把商品名、价格、图片 URL 写进购物车表：

```java
cart.setGoodsSn(goods.getGoodsSn());
cart.setGoodsName(goods.getName());
cart.setPicUrl(goods.getPicUrl());
cart.setPrice(product.getPrice());
```

和订单明细快照同手法，但动机完全不同：

| | 购物车快照 | 订单明细快照 |
|------|-----------|-------------|
| **动机** | 性能：空间换时间 | 法律：历史冻结 |
| **效果** | 列表不用 join 商品表，查一张 cart 表就够 | 下单后的数据永远不变，对账凭证 |
| **能改吗** | 能！每次加购都会覆盖，旧快照无所谓 | 绝对不能！ |

读代码时判断标准：**"这个冗余字段，改了会出问题吗？"** 改了也无所谓 = 性能冗余；改了就要命 = 历史冻结。

---

#### 观察二：历史痕迹 —— "改为同步更新"

changeNum 里有一段注释：

```java
// 改数量改为同步更新，接口返回即代表数据库已落库，避免异步写导致前端读到旧值。
Cart updateCart = new Cart();
updateCart.setId(cartId);
updateCart.setNumber(number);
cartMapper.updateById(updateCart);
```

"改为"两个字是代码考古的关键线索：

- **曾经**：数量变更走异步（大概率发 MQ → 消费者写库），目的是削峰
- **问题**：前端改了数量后立即刷新列表，读到旧值（MQ 还没消费）
- **改回来**：回归同步写库，牺牲一点点吞吐，换取用户体验一致性

判断：购物车改数量 QPS 极低（不是秒杀），异步的收益微乎其微，但"看到旧值"的体验伤害是实打实的。这是一个"过度设计被现实打回来"的案例。

---

#### 观察三：类型债 —— userId Long vs Integer

```java
// Cart 实体
private Integer userId;  // ← Integer

// 但系统其他地方 userId 都是 Long
public void add(Cart cart, Long userId) {
    // ...
    cart.setUserId(Math.toIntExact(userId));  // ← Long → int，超 21 亿直接抛异常
}
```

`updateChecked` 更是直接在 SQL 条件里做了转换：

```java
.eq(Cart::getUserId, Math.toIntExact(userId))
```

这行 SQL 条件还有个隐含设计：**WHERE cart_id = ? AND user_id = ?**。

不是"查出 cart 再判断是不是本人的"，而是"直接在 SQL 条件里带 userId"。好处：**没有 TOCTOU 窗口**（Time-of-Check-Time-of-Use，查出后到更新前中间不可能被改）。

缺点：改了别人的购物车只是返回 0 行，不像"先查再抛异常"那样有明确的错误提示。

| 问题 | 说明 |
|------|------|
| 类型不一致 | 商品/订单/用户服务都用 Long，购物车用 Integer |
| 风险 | 用户 ID 超 21.4 亿 → `Math.toIntExact()` 抛异常 |
| 影响 | 短期内无风险（用户量没到这个级别），但这是一个设计债 |
| 归属校验 | `eq(Cart::getUserId, userId)` 防止横向越权，比先查再判断更安全 |

### 聚合写入与对账式更新

商品不是一个单表，而是一个聚合根：`goods`（主表）+ `goods_specification`（规格） + `goods_attribute`（属性） + `goods_product`（货品/SKU）。GoodsMutationSupport 统一管理这个聚合的写入。

#### saveGoodsRelated：全量新增

```
saveGoodsRelated(GoodsSaveRelatedReqVO)
│
├─ 3 层校验（商品名唯一、货品合法性、至少一个默认货品）
├─ INSERT goods 主表 → 拿到自增 ID → 回写 goodsSn = ID
├─ 子表批量 setId(null) + 关联 goodsId → INSERT 三张子表
└─ evictGoodsDetailCache(goodsId)
```

`@Transactional` 保证 4 张表要么全部写入，要么全部回滚。

#### updateGoodsRelated：增删改对账

```
updateGoodsRelated(GoodsSaveRelatedReqVO)
│
├─ 校验（同上）
├─ UPDATE goods 主表（ID 已有，直接更新）
├─ syncSpecifications / syncAttributes / syncProducts
│   ├─ id 为空 → INSERT（新增子项）
│   ├─ id 不为空 → UPDATE（已有子项）
│   └─ 数据库有但前端没传 → DELETE（运营删了）
└─ evictGoodsDetailCache(goodsId)
```

**为什么不用"全删重插"？**

goods_product 的 ID 被外部引用（购物车表、订单明细表、库存流水表）。全删重插会导致自增 ID 全部变化，所有外部引用断裂。对账（增删改）保持现有子项的 ID 不变，只修改内容。

```
全删重插：
  product id=30(黑色/128G) → 删除 → INSERT id=40(黑色/128G)
  购物车里存的 productId=30 → 悬空引用 ❌

对账：
  product id=30(黑色/128G) → id 有值 → UPDATE 内容
  购物车里存的 productId=30 → 仍然有效 ✅
```

#### deleteGoodsRelatedByGoodsId：聚合物理删除

```
deleteGoodsRelatedByGoodsId(goodsId)
│
├─ DELETE goods WHERE id = ?
├─ DELETE goods_specification WHERE goods_id = ?
├─ DELETE goods_attribute WHERE goods_id = ?
├─ DELETE goods_product WHERE goods_id = ?
├─ ES 删文档（如果 ES 模块存在）
└─ evictGoodsDetailCache(goodsId)
```

删除时全删子表是安全的——整个聚合根不存在了，外部引用（订单、购物车里的 productId）也失去了意义。这和"更新时全删重插导致 ID 变化"完全不同。

### 库存差量铁律

#### 核心方法：adjustExistingProductStock

```java
adjustExistingProductStock(GoodsProduct incoming, GoodsProduct existing)
//                        ^^^^^^^^ 前端表单提交的    ^^^^^^^^ 数据库当前真值
```

**为什么不能覆盖？**

管理端编辑商品时，货品库存可能已经被并发下单改过了。直接覆盖会抹掉下单扣减。

#### 时序推演：覆盖 vs 差量

两个场景的关键区别在于：**并发卖出发生在"读库之前"还是"读库之后、写库之前"。**

##### 场景一：卖出发生在读库之前 → 两个都"失效"（但不丢数据）

卖出在 `updateGoodsRelated` 启动前已经落库，后端读到的是 7，不是 10。

```
时刻    运营页面(快照)      数据库真值        后端代码
T0     显示 10              10               —
T1     运营输入 20          10               —（纯前端操作，后端毫不知情）
T2     （页面不刷新）         → 7            下单链路：number = 7 ← 卖出在事务开始前
T3     点"保存"              7               updateGoodsRelated 开始
                                            → 重新读库：existing.number = 7
                                            → 表单传入：incoming.number = 20
                                            → delta = 20 - 7 = 13
T4     —                     20              覆盖法：SET number = 20
                                             差量法：number = number + 13
                                             → 结果都是 20
                                            运营以为 +10，实际 +13
                                            但不丢数据 ✅
```

此场景覆盖法和差量法结果一样（都是 20），问题不在数据正确性，而在运营预期偏差。

##### 场景二：卖出发生在读库之后、写库之前 → 覆盖法丢数据，差量法救回来

这是真正的并发竞态：事务内读了 10，但执行 UPDATE 前被插了一脚。

```
时刻    数据库真值        后端代码（updateGoodsRelated 事务内）
T0      10               —
T1      10               事务开始 → 重新读库：existing.number = 10
                                          → 算出 delta = 20 - 10 = +10
                                          → ↓ （就这几毫秒里，另一笔下单卖了 3 件入账）
T2       7               —（事务内读到的还是 10，已经过时了）
T3       7               执行 UPDATE：
                            覆盖法：SET number = 20
                            差量法：number = number + 10
T4      覆盖法 → 20       差量法 → 17
        ❌ 那 3 件凭空消失  ✅ 3 件被保住（7 + 10 = 17）
```

**差量法赢在哪里？**

```
覆盖法：SET number = 20
  ↑ 20 是 Java 里算好的值，基于过时的"10"。
  数据库不管你现在是 7 还是 100，直接写成 20。

差量法：SET number = number + 10
  ↑ "number + 10" 是让数据库自己算。
  数据库拿当前真值 7，往上加 10 得到 17。
  Java 里算 delta 时用的 10 确实过时了，但 "+10" 这个动作本身是原子的、基于当前真值的。
```

**核心：差量法把"基于什么值做运算"从 Java 内存交给了数据库。Java 里的值会过时，数据库里的 `number = number + N` 不会。**

#### incoming.setNumber(null) 的作用

```java
int stockDelta = incoming.getNumber() - existing.getNumber();  // 算差值
incoming.setNumber(null);  // ← 关键！防止后续 updateBatchById 覆盖库存

// addStock/reduceStock 单独执行
goodsProductService.addStock(incoming.getId(), stockDelta);

// 后续 updateBatchById 生成的 SQL 不包含 SET number =
// 因为 MyBatis-Plus 默认策略：字段为 null 时不生成到 SQL
```

两条 SQL，各司其职：

```
① addStock(30, +13) → UPDATE goods_product SET number = number + 13 WHERE id = 30  （改库存）
② updateBatchById   → UPDATE goods_product SET price=?, specs=?, ... WHERE id = 30 （改其他字段）
```

setNumber(null) 就是让第②条 SQL 不碰 number 字段。

#### 冻结库存保护

减库存时额外校验：不允许减到低于已锁定库存（lockedStock）。

```java
if (stockDelta < 0) {
    int lockedStock = existing.getLockedStock();  // 正在支付流程中的数量
    int afterReduce = existing.getNumber() + stockDelta;
    if (afterReduce < lockedStock) {
        throw new BusinessException("库存不足，当前冻结库存 " + lockedStock);
    }
}
```

逻辑：库存 10 件，lockedStock = 6（6 件正在支付），运营想减到 3 → afterReduce = 3 < 6 → 抛异常。语义：6 个人正在付钱，你减到只剩 3，注定有人付了钱拿不到货。

#### 为什么 delta 用表单值算，不用数据库真值算？

```
delta = incoming.number - existing.number
        ^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^
        表单值（20）       数据库真值（10 或 7）

为什么不用数据库真值算？即：delta = 20 - 7 = 13
```

两个值代表完全不同的东西：

| 值 | 代表什么 |
|------|---------|
| **表单值（20）** | 运营的意图——"我要让库存变成 20" |
| 页面快照（10） | 运营做决策的依据——"我以为现在有 10 件，所以加 10 件" |
| **数据库真值（10 或 7）** | 世界的真相——"实际上已经发生了这些变化" |

如果 delta 用数据库真值算：

```
delta = 20 - 7 = 13
→ 入库 13 件

账本：
  10 → 7（下单卖了 3 件）→ 20（运营加了 13 件）

问题："卖了 3 件"和"运营加了 10 件"被裹成一笔"+13"。
审计时没人说得清——到底卖了几件？到底加了几件？
```

正确做法——delta 用运营看到的值算：

```
运营看到 20，想要 30 → delta = 30 - 20 = 10（加 10 件）
不管中间数据库变成多少，"+10" 这个意图是独立的。

账本：
  10 → 7（下单卖了 3 件）→ 17（运营加了 10 件）

每一笔都分得清：卖 3 件是卖 3 件，加 10 件是加 10 件。
```

> **一句话：表单值 = 运营意图（"我要加多少"），数据库值 = 世界真相（"发生了什么"）。用后者算 delta 等于把"已经发生的事"和"运营想做的事"搅在一起，账本分不清。正确的 delta 应该永远基于运营看到的值：`表单值 - 页面快照值`，而不是 `表单值 - 数据库当前值`。**

当前代码 `delta = incoming.number - existing.number` 用的是数据库真值，这是为了适配 `addStock` / `reduceStock` 的 API（它们只需要一个 delta 数字）。真正的"意图"delta 应该在 `syncProducts` 里算：`intentDelta = incoming.number - pageSnapshot.number`，然后在 `adjustExistingProductStock` 里用 `existing.number + intentDelta` 得到目标值再做判断。当前实现把"卖出的 3 件"和"运营加的 10 件"算成一笔，是不精确的——虽然数据不丢，但库存账本无法溯源这 3 件是被卖掉的还是运营少加的。

#### 写路径联动

GoodsMutationSupport 每一次写操作末尾都调 `evictGoodsDetailCache(goodsId)`：

```

```

闭环：写删（evict）→ 读填（queriedOnMiss）→ TTL 兜底（300s）。

#### 三大问题对照表

| 问题 | 现象 | 本项目现状 | 标准解法 |
|------|------|-----------|---------|
| **穿透** | 查不存在的 goodsId，每次都打到 DB | **未防。** 未缓存 null 值（相当于 `disableCachingNullValues`），恶意请求可以打爆 DB | 缓存空对象（value=null，TTL 短一些）或布隆过滤器 |
| **击穿** | 热点 key（如爆款商品详情）在 TTL 过期瞬间，大量请求同时回源查 DB | **未防。** 没有互斥锁/分布式锁保护回源过程，Cache-Aside 模式下多个请求同时 miss → 同时查库 | 分布式锁（阶段 0 的 `ORDER_SUBMIT_DEDUP_KEY` 同思路）+ 双重检查；或"永不过期 + 后台异步刷新" |
| **雪崩** | 大量 key 在同一时刻过期（如系统启动时统一预热），瞬间巨量请求直接打 DB | **部分暴露。** TTL 固定 300 秒无随机抖动，如果某个时间点集中写缓存（如全量预热），300 秒后会同时过期 | TTL 加随机值（如 300 + random(0, 60)），错开过期时间 |

```
为什么穿透/击穿还没出问题？
  商品详情页访问量不大，且单个 goodsId 的 4 表查询很快（毫秒级）。
  随着商品量和用户量增长，这两点是迟早要补的。

雪崩为什么"部分暴露"？
  当前没有全量预热机制，缓存是"谁被访问谁建"的懒加载。
  所以 key 的过期时间天然分散，不是同时过期。
  但如果未来加了预热脚本，就会暴露。
```

### 跨三存储删除的教训

`deleteGoodsRelatedByGoodsId` 涉及三个存储：

```java
@Transactional(rollbackFor = Exception.class)
public boolean deleteGoodsRelatedByGoodsId(Long goodsId) throws IOException {
    goodsMapper.deleteById(goodsId);                                  // MySQL 主表
    goodsSpecificationService.remove(...);                             // MySQL 子表
    goodsAttributeService.remove(...);                                 // MySQL 子表
    goodsProductService.remove(...);                                   // MySQL 子表
    if (goodsElasticSyncSupport != null) {
        goodsElasticSyncSupport.deleteGoodsFromEs(goodsId);           // ES
    }
    evictGoodsDetailCache(goodsId);                                    // Redis
    return true;
}
```

#### 事务边界与"不一致窗口"

`@Transactional` 只保护 MySQL 操作。ES 和 Redis 在事务之外：

```
@Transactional 事务边界
┌─────────────────────────────────────────────────────────┐
│  DELETE goods / specs / attrs / products                │
│  → MySQL COMMIT ✅（4 张表全部删除）                    │
└─────────────────────────────────────────────────────────┘
                                                           ← 窗口：MySQL 已删，ES/Redis 还没删
  deleteGoodsFromEs(goodsId)                               → ES DELETE（可能失败）
  evictGoodsDetailCache(goodsId)                           → Redis DELETE（可能失败）
```

#### 各种异常的对策

| 异常 | 后果 | 当前对策 | 理想对策 |
|------|------|---------|---------|
| MySQL 删除失败 | 事务回滚，三存储都不动 | `@Transactional` 自动保证 ✅ | — |
| ES 删除失败 | MySQL 已删，ES 还有文档 | 抛 IOException → 事务仍在执行（ES 在事务外）→ MySQL 能回滚吗？**不能！** ES 删除代码在事务方法内但不在事务管理范围内 | Outbox：只写 MySQL outbox 表，异步重试 ES |
| Redis 删除失败 | MySQL 已删，缓存还在 | 靠 TTL 300s 自愈，但期间可能读到旧缓存再回填（如果 key 被其他操作重建） | — |

#### 教训

1. **跨存储操作无法放在一个 ACID 事务里。** ES 和 Redis 不参与 MySQL 的事务管理，`@Transactional` 只保护 JDBC 连接。
2. **删除失败时的行为取决于 Elasticsearch 客户端的异常处理。** 如果抛 IOException → `@Transactional(rollbackFor = Exception.class)` 会回滚 MySQL → 三存储都干净。但 ES 的 IOException 发生在事务提交之后（代码顺序上 ES 在事务方法内但实际上不受事务保护），实际行为需看具体 ES 客户端实现。
3. **当前最可靠的兜底是 TTL。** Redis 缓存 300 秒后自动过期；ES 文档需要额外保障。

### 二、领券：三层并发防护

入口：[CouponAcquireSupport.receive()](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/java/com/wayn/domain/promotion/support/coupon/CouponAcquireSupport.java)

```
用户请求 receive(userId, couponId)
  │
  ├── 第一层：Redis 分布式锁
  │   key = COUPON_RECEIVE_LOCK:{userId}:{couponId}
  │   timeout = 2 秒
  │   粒度：用户+券模板 维度
  │   作用：同一用户领同一张券的请求串行化，快速拒绝重复点击
  │
  ├── 第二层：业务校验
  │   ✓ 券模板存在
  │   ✓ 券状态为上架（status == 1）
  │   ✓ 券未过期
  │   ✓ 用户未重复领取（COUNT shop_member_coupon WHERE userId AND couponId）
  │
  └── 第三层：数据库条件更新（最后防线）
      UPDATE shop_coupon
      SET receive_num = receive_num + 1
      WHERE id = #{couponId}
        AND receive_num < num          ← 关键条件
      
      updated == 0 → 库存已耗尽 → 抛异常
```

#### 第三层的 SQL（关键）

[ShopCouponMapper.xml](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/resources/mapper/promotion/ShopCouponMapper.xml)

```xml
<update id="updateReceiveNum">
    update shop_coupon
    set receive_num = receive_num + 1
    where id = #{couponId}
      and receive_num <![CDATA[ < ]]> num
</update>
```

`receive_num < num` 是核心，它利用 MySQL InnoDB 的**行级锁**保证：即使 Redis 锁被绕开，同一时刻多个 UPDATE 竞争同一行时，只有一个能成功将 `receive_num` 从 N-1 递增到 N（此时 `receive_num < num` 条件不再满足，其余 UPDATE 影响 0 行）。

#### 为什么需要三层？

| 层级 | 失败时 | 作用 |
|------|--------|------|
| Redis 锁 | 快速拒绝，不进入数据库 | 拦截 99% 的并发冲突 |
| 业务校验 | 精确拒绝不合规请求 | 拦截业务层面的无效请求 |
| 条件 UPDATE | 原子操作，数据库兜底 | 防止超发 |

### 三、锁粒度对比

| 场景 | 锁 Key | 粒度 | 含义 |
|------|--------|------|------|
| 领券 | `COUPON_RECEIVE_LOCK:{userId}:{couponId}` | 用户+券模板 | 同一用户同一张券串行，不同用户/不同券不互斥 |
| 交易锁 | 支持多锁（`executeWithLocks`） | 按需组合 | 批处理时保护多个订单号 |

#### 为什么领券锁粒度是 userId:couponId 而非 couponId？

- 如果用 `couponId` 全局锁 → 热门券所有用户排队 → 性能瓶颈
- 用 `userId:couponId` → 不同用户领同一张券互不阻塞 → 高并发友好

### 五、并发漏洞：锁释放早于事务提交

#### 漏洞位置

[CouponAcquireSupport.receive()](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/java/com/wayn/domain/promotion/support/coupon/CouponAcquireSupport.java) 第 59-90 行

#### 根因

锁释放和事务提交存在时序错位。关键代码路径：

```java
@Transactional  // ← 事务边界（方法入口→出口）
public Boolean receive(...) {
    return tradeLockSupport.executeWithLock(lockKey, ..., () -> {
        // ...
        // ┌─ 锁内 ──────────────────────────┐
        // │  count 校验通过                  │
        // │  updateReceiveNum (未提交)        │
        // │  save INSERT (未提交)             │
        // └──────────────────────────────────┘
        // ↑ supplier.get() 返回后，finally 块释放锁
    });
    // ← 方法返回后，Spring 提交事务
}
```

[RedisTradeLockSupport.executeWithLock()](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/common/RedisTradeLockSupport.java) 第 56-65 行：

```java
try {
    return supplier.get();   // 业务执行
} finally {
    redisLock.unLock(lockKey); // 立即释放锁，不等事务提交
}
```

#### 攻击时序

线程A: receive() 开始
       ├─ Spring 开启事务            ← 事务先开
       ├─ 拿到 Redis 锁
       ├─ count = 0 → 通过；updateReceiveNum（未提交）；save 用户券（未提交）
       ├─ 释放锁                     ← 锁先放！
       └─ 方法返回 → 事务提交         ← 提交在后面
线程B: 在 A 释放锁之后、提交之前抢到锁
       ├─ count(userId, couponId) → A 的插入还没提交，B 读不到 → count = 0 → 通过！
       └─ → 同一用户领到第二张券（限领被突破）
                                        
结果：同一用户同一张券两条记录（限领被突破）

#### 为什么 MySQL REPEATABLE READ 挡不住？

- 事务 B 的快照在第一句 SQL 时建立
- 如果此时事务 A 还没提交，B 的快照里没有 A 的 INSERT
- `COUNT` 基于快照读，看不到未提交数据 → 结果为 0 → 通过

#### 影响范围

- 只有 "同一用户领同一张券" 这个场景受影响
- 窗口期极短（锁释放 → 事务提交之间），但并发大时必然触发
- `updateReceiveNum` 的条件更新能保护库存总量不超发，但**不能保护用户去重**

#### 修复方案

**方案一（推荐，最简单）：数据库唯一约束**

```sql
ALTER TABLE shop_member_coupon ADD UNIQUE KEY uk_user_coupon (user_id, coupon_id);
```

即使 count 校验漏过去，第二个 INSERT 也会报唯一键冲突 → 事务回滚。

**方案二：事务提交后再放锁**

利用 Spring `TransactionSynchronization`：

```java
// 在 executeWithLock 调用处改为：
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            redisLock.unLock(lockKey);
        }
    }
);
```

**建议两个方案同时采用：**
- 方案一 → 数据库层兜底
- 方案二 → 修复锁时序，语义正确

### 六、策略查找 null 返回与暴露时机

#### 当前行为

[DiamondJumpContext.getInstance()](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/java/com/wayn/domain/promotion/strategy/diamond/DiamondJumpContext.java) 传入非 0、1 的 jumpType 时返回 null：

```java
public DiamondJumpTypeInterface getInstance(Integer jumpType) {
    return map.get(jumpType);  // jumpType=2 → null
}
```

#### null 不等于立即 NPE

返回 null 本身不抛异常。NPE 发生在**第一次对 null 调用方法**时：

```java
DiamondJumpTypeInterface s = context.getInstance(2);  // 返回 null，没炸
// ... 中间可能隔了调用链的好几层 ...
s.getGoods(page, diamond);  // ← 在这里 NPE
```

#### 暴露时机：为什么裸 null 最危险

```
开发阶段  ─  测试数据只有 jumpType=0 和 1，一切正常
上线运行  ─  运营新建金刚位，jumpType 配成 2（URL 跳转）
          用户点击该金刚位
          getInstance(2) → 返回 null     ← 静默
          代码继续执行                   ← 静默
          s.getGoods() → NPE 💥         ← 数据触发，偶发炸
```

特点：
- **偶发**：只有点击特定金刚位的用户才报错
- **数据触发**：本地永远复现不了（测试库没有那条数据）
- **排查困难**：日志里只有 NPE 栈，不会打印"jumpType=2 未注册"，运营可能几天前改的配置

#### 三类失败策略

| 策略 | 代码 | 暴露时机 | 调用方感知 |
|------|------|---------|-----------|
| ❌ 裸 null | `return map.get(jumpType)` | 运行时，方法调用时 | **无感知**，安静地返回 null |
| ✅ fail-fast 抛异常 | `throw new BusinessException(...)` | **立即**，getInstance 内部 | 必须处理或传播 |
| ✅ Optional | `return Optional.ofNullable(...)` | **编译期**，类型签名强制处理 | 不处理编译不过 |
| ✅ 默认策略 | `return map.getOrDefault(key, default)` | 永不暴露 | 静默降级，业务不中断 |

#### 对比：支付模块做了正确的选择

```java
// 金刚位（当前） — 裸 null
public DiamondJumpTypeInterface getInstance(Integer jumpType) {
    return map.get(jumpType);
    // 运营误配 jumpType=2 → 返回 null → 某次请求神秘 NPE
}

// 支付模块 — fail-fast
public PayTypeInterface getInstance(Integer payType) {
    PayTypeInterface payTypeInterface = map.get(payType);
    if (payTypeInterface == null) {
        throw new BusinessException(ReturnCodeEnum.ORDER_SET_PAY_ERROR);
        // 支付类型不存在 → 当场炸 → 日志明确 → 5 分钟定位
    }
    return payTypeInterface;
}
```

#### 核心原则

> 让调用方无法忽略错误。裸 null 恰恰是最容易被忽略的那一种。

- **fail-fast**：在第一现场就炸，堆栈直指问题
- **Optional**：编译期强制调用方处理缺失情况
- **默认策略**：适用于有合理降级方案的场景（如"未知类型按栏目处理"）
- **裸 null**：没有理由，永远不要返回

### "一个信号，两种语义"

`OrderStockSupport` 中 `saveFlow` 被两处调用，都是"写流水 → 看返回值 → 决定是否动库存"，但返回值 `false` 的含义截然相反：

| | freezeStock | processOrderGoodsStockChange |
|---|---|---|
| **调用场景** | 下单冻结（首次执行） | 确认/释放/回补（补偿重试） |
| **flowKey 前缀** | `ORDER_FREEZE:` | `ORDER_CONFIRM:` / `ORDER_RELEASE:` / `ORDER_REFUND_RETURN:` |
| **saveFlow=false 的含义** | 同一订单同一 SKU 已经冻结过 → **bug** | 该 SKU 的库存副作用已经执行过 → **正常幂等** |
| **处理方式** | `throw BusinessException` → 事务回滚 | `continue` → 跳过该 SKU |
| **为什么不同** | 冻结调用方不做重试，重复 = 脏数据 | outbox at-least-once，重复 = 预期行为 |

```
         saveFlow(flowKey)
              │
    ┌─────────┴─────────┐
    │                   │
   true               false
    │                   │
    │              ┌────┴────┐
    │         freezeStock   processOrderGoodsStockChange
    │              │              │
    │           throw!        continue
    │         "这是bug"     "正常，上次做过了"
    │
    ▼
  UPDATE ... WHERE >= N
```

同一行 `if (!flowSaved)`，同一个 `saveFlow` 方法，返回值都是 `false`——但因为调用方对"重复"的容忍度不同，相同的信号演变成**完全相反的处理策略**。

### flowKey 结构

```
flowKey = PREFIX + ":" + bizId + ":" + productId
```

| 前缀 | 完整示例 | 含义 |
|------|---------|------|
| `ORDER_FREEZE:` | `ORDER_FREEZE:SN20240101001:123` | 订单 SN20240101001 对 SKU 123 的冻结 |
| `ORDER_CONFIRM:` | `ORDER_CONFIRM:100:123` | 订单 ID=100 对 SKU 123 的确认 |
| `ORDER_RELEASE:` | `ORDER_RELEASE:100:123` | 订单 ID=100 对 SKU 123 的释放 |
| `ORDER_REFUND_RETURN:` | `ORDER_REFUND_RETURN:100:123` | 订单 ID=100 对 SKU 123 的退款回补 |

#### 结构原则

- `bizId` 在冻结时为 `orderSn`（下单时还没有 orderId），确认/释放/回补时为 `orderId` 字符串
- `productId` 保证同一订单的多个 SKU 互不干扰——A SKU 确认成功、B SKU 确认失败，A 不会因 B 重试而重复执行
- `inventory_flow` 表 `flow_key` 字段有唯一约束——这是整个幂等体系的基础

### 双轨校验：内存 + MySQL

```java
// freezeStock 方法内，两条线串行：

validateAvailableStock(cart, product, required);  // ① 内存校验
    └─ if (product.number - required < 0) → throw "库存不足"
       └─ 目的：提前拦截，生成友好的中文错误提示

goodsProductService.freezeStock(productId, N);     // ② MySQL 条件更新
    └─ UPDATE ... SET number = number - N WHERE number >= N
       └─ 目的：真正的并发安全，affected_rows=0 时回滚
```

| | 内存校验 | MySQL 条件更新 |
|---|---|---|
| **依赖** | `product.getNumber()` 查询时的快照 | 行级锁下读取 `number` 当前值 |
| **并发安全** | ❌ 不安全（快照过期、多线程同时通过） | ✅ 安全（InnoDB 行锁 + WHERE 条件） |
| **失败消息** | 友好的 "商品【XX】【规格 YY】库存不足" | `BusinessException("商品货品冻结库存不足")` |
| **如果只用它** | 超卖 | 用户看到技术错误信息 |

两者不是"二选一"而是"串行配合"。内存校验挡住 99% 的明显不足请求，MySQL 兜底挡住 1% 的并发穿透。内存校验失败时用户立刻看到友好提示，MySQL 失败时说明发生了极端并发——此时抛异常回滚，库存状态安全。

#### 为什么不能只依赖内存校验？

```
时刻 T0: 数据库 number = 10
时刻 T1: 线程 A 查询 product.number = 10 → 校验通过 ✅
时刻 T2: 线程 B 查询 product.number = 10 → 校验通过 ✅
时刻 T3: 线程 A UPDATE WHERE number >= 5 → number = 5  ✅
时刻 T4: 线程 B UPDATE WHERE number >= 5 → number = 0  ✅  （MySQL 保证不超卖）
```

两个线程的内存校验都通过了（都看到 10），但 MySQL 的条件更新串行化了实际扣减，最终 `number=0`，没有超卖。

### 二、Redis 库存快照体系

#### 快照三把 Key + 分桶守恒

Redis 库存预占涉及三类 Key，刷新任务负责写其中两类：

```
刷新阶段（refreshStockSnapshot，每 5 分钟）：
  ┌─────────────────────────────────────────────────────┐
  │ MySQL goods_product.number = 100                    │
  │               │                                     │
  │    ┌──────────┼──────────┐                          │
  │    ▼          ▼          ▼                          │
  │ ① available  ② bucketCount  ③ bucket_available      │
  │  (全局快照)   (桶数标记)      (分桶快照)              │
  │                                                    │
  │ trade:stock:         trade:stock:     trade:stock:  │
  │ available:123=100    bucket:count:    available:123:│
  │                      123=4           bucket:0=25    │
  │                                      bucket:1=25    │
  │                                      bucket:2=25    │
  │                                      bucket:3=25    │
  └─────────────────────────────────────────────────────┘

下单阶段（preDeduct，每次下单）：
  ┌─────────────────────────────────────────────────────┐
  │ Lua 脚本使用三类 Key：                                │
  │                                                    │
  │ ① available  = 可售快照（读，判断库存够不够）          │
  │ ② reserved   = 预占总量（读+写，并发闸门计数）         │
  │ ③ order      = 订单幂等（读+写，防重复预占，30s TTL）  │
  │                                                    │
  │ ① 来自刷新任务写入，②③ 由 Lua 脚本动态产生             │
  └─────────────────────────────────────────────────────┘
```

分桶后每个桶有独立的三把 Key：`available:bucket:N`、`reserved:bucket:N`、`order:bucket:N`。预占和释放路由到同一个桶，保证桶内守恒。

#### 刷新任务的"热点优先"

```java
// RedisStockSnapshotSupport.listLatestProducts()
SELECT id FROM shop_goods_product
WHERE del_flag = false
ORDER BY update_time DESC
LIMIT 500
```

策略是 **`ORDER BY update_time DESC`**——不是全量刷新，也不是随机抽样，而是**最近被更新过的 SKU 优先**。理由：

- 刚被下单的 SKU 库存变化最快，Redis 快照最容易过期，优先刷新收益最大。
- 长期没人买的 SKU 库存不变，Redis 快照不过期也无所谓。
- 每次只扫 500 条，避免全表扫描压垮 MySQL。

### 三、库存流水对账体系

#### "以流水反推"的对账思路

```
inventory_flow（账本）           goods_product.locked_stock（实物）
        │                                │
  FREEZE:    +N                        数据库当前值
  CONFIRM:   -N
  RELEASE:   -N                         ↓
  REFUND:    不影响                  比对：期望值 vs 实际值
        │
        ▼
  期望值 = Σ(流水影响)
```

#### 三道保护

| 层次 | 机制 | 防什么 |
|------|------|--------|
| ① 流水幂等 | `saveFlow` → `DuplicateKeyException` → `continue`/`throw` | outbox 重试导致同一副作用重复执行 |
| ② 库存守卫 | `WHERE locked_stock >= N` / `WHERE number >= N` | 重复扣库存导致 locked_stock 为负或 number 虚高 |
| ③ 修复守卫 | `WHERE locked_stock = actualLockedStock` | 对账修复覆盖并发发生的新库存变更 |

三层方向不同：

```
① 防"同一条消息重复执行" → 流水唯一键挡住
② 防"同一操作多次执行" → MySQL 条件更新挡住
③ 防"修复操作踩到并发业务" → CAS 条件挡住
```

### 五、关于 SKU 分桶的诚实判断

> 代码量是上去看的，但不要让它变成误解。
>
> 项目实现了热点 SKU 分桶预占（`RedisStockBucketRouter` + `RedisStockPreDeductSupport.routeStockKeys()`），但我判断在当前单机部署形态下无吞吐收益。
>
> **证据**：`application-dev.yml` 中 Redis 配置为单点 —— `host: 127.0.0.1`，`port: 6379`，无 `cluster.nodes` 无 `sentinel.master`。Redis 命令执行是单线程的，所有 Lua 脚本顺序排队，分桶不改变总操作数与排队顺序。
>
> **它的价值在 Redis Cluster/分片场景下才成立**：不同桶的 Key 落在不同 hash slot → 不同节点 → 不同节点的 Lua 脚本真正并行执行 → 吞吐量随桶数线性增长。
>
> **默认配置也印证了这是默认关闭的可选优化**：`bucketCount=1` 表示不分桶，仅当业务方主动配置 `>1` 时才启用。当前环境下即使启用了，也只是多写了几组 Key，没有并发收益。

### 设计要点

#### 响应式排序

```java
this.steps = steps.stream()
        .sorted(Comparator.comparingInt(OrderSubmitStep::order))
        .toList();
```

Spring 注入的 `List<OrderSubmitStep>` 顺序不可靠，必须按 `order()` 显式排序。

**order 相同时会发生什么？** `Comparator.comparingInt` 返回 0（视为相等），`Stream.sorted` 是稳定排序，相等元素保持原有相对顺序——即 Spring 注入顺序。此时排序静默退化到 Spring 注入顺序，这正是构造器注释明确要避免的事。注入顺序"看起来确定"但不是契约：换 JDK 版本、加一个 Bean、换构建方式都可能改变。"能跑"是这类 bug 最危险的地方。

#### 编号留白

留白的作用有两层：

**第一层（表面）：方便插入新步骤。** 如在 100→200 之间插入风控校验，赋 150 即可，不碰任何现有编号。

**第二层（本质）：让编号碰撞物理上不可能。** 稀疏的数字空间保证每个步骤独占一个编号，`Comparator.comparingInt` 的排序结果永远唯一、永远不依赖 Spring 注入顺序。留白不是为"未来的步骤"预留空间——是为"当前步骤的确定性排序"提供结构性保证。插入新步骤只是这个设计的副产品。

| 区间 | 用途 | 示例 |
|------|------|------|
| 100-199 | 前置校验 | 查重、风控、限购 |
| 200-299 | 上下文准备 | 地址、购物车、优惠券快照 |
| 300-399 | 资源扣减 | 库存冻结 |
| 400-499 | 实体组装 | DTO → Entity |
| 500-599 | 持久化 | 订单落库 |
| 600-699 | 后置消息 | 关单延迟、通知 |

#### EnumMap 白名单定义

| 当前状态 | 允许转到的状态 |
|---------|---------------|
| `STATUS_CREATE` | `PAY`, `CANCEL`, `AUTO_CANCEL` |
| `STATUS_PAY` | `REFUND`, `SHIP` |
| `STATUS_REFUND` | `REFUND_CONFIRM` |
| `STATUS_SHIP` | `CONFIRM`, `AUTO_CONFIRM` |

#### validateTransition vs applyExpectedStatus 分工

| | validateTransition / canTransition | applyExpectedStatus |
|------|-----------------------------------|---------------------|
| **查什么** | `EnumMap` 内存白名单 | SQL `WHERE order_status = ?` |
| **防什么** | 非法流转（已取消的订单被当成已支付） | 并发覆盖（校验后、UPDATE 前被别的线程改掉） |
| **失败表现** | 抛异常 / 返回 false | `affected_rows = 0` |
| **何时执行** | UPDATE 之前（应用层校验） | UPDATE SQL 之中（数据库层 CAS） |
| **能省略吗** | 不能——只有 apply 的话，撞对状态就能跳过合法流转 | 不能——只有 validate 的话，两线程同时通过校验，后写覆盖先写 |

#### 为什么必须配对

```
① validate:      CREATE → SHIP？  白名单里没有 → ❌ 拒绝
② apply:         WHERE status=PAY  → 防止验证通过后被改掉

两个缺一不可：
  只有 ① → 两个人同时通过校验，后写的覆盖前写的
  只有 ② → 如果 WHERE 条件凑巧命中（状态刚好是期望值），任何流转都能通过
```

#### 五个并发入口清单

所有入口都通过 `OrderStateTransitionSupport` 收口，规则集中在一处：

| 入口 | 文件 | 校验方式 | 期望状态 | 目标状态 |
|------|------|---------|---------|---------|
| **支付回调** | `PaymentCallbackSupport` | `canTransition` | `STATUS_CREATE` | `STATUS_PAY` |
| **用户取消** | `OrderCancellationSupport` | `canTransition` | `STATUS_CREATE` | `CANCEL / AUTO_CANCEL` |
| **系统超时关单** | `OrderCancellationSupport`（同一方法） | `canTransition` | `STATUS_CREATE` | `CANCEL / AUTO_CANCEL` |
| **管理员发货** | `AdminOrderShipmentSupport` | `validateTransition` | `STATUS_PAY` | `STATUS_SHIP` |
| **管理员退款** | `AdminOrderRefundSupport` | `validateTransition` | `STATUS_REFUND` | `STATUS_REFUND_CONFIRM` |
| **用户退款** | `OrderLifecycleSupport` | `validateTransition` | sourceStatus | `STATUS_REFUND` |
| **用户确认收货** | `OrderLifecycleSupport` | `validateTransition` | sourceStatus | `STATUS_CONFIRM` |

#### 未知状态的方向性

`resolve(Short)` 返回 `null` 时，代表数据库中出现了状态机不认识的脏数据。此时：

```java
// canTransition: null → false（拒绝一切操作）
// validateTransition: 不直接面对 Short，Enum 不存在的情况编译期就杜绝了
```

**设计态度：未知状态一律拒绝，不猜测意图。** 终态（`CONFIRM`、`CANCEL` 等）也没有在 `transitions` 中注册出边，`get()` 返回 `null` → `canTransition` 返回 `false`，自然阻止了"已完成的订单被再次修改"。

#### 收口 vs 散落：状态机 vs 各写 if/else

##### 散落 if/else 的样子

```java
// 支付回调
if (order.getStatus() == STATUS_CREATE) { ... }

// 用户取消
if (order.getStatus() == STATUS_CREATE && order.getStatus() != STATUS_PAY) { ... }
//                                              ↑ 多余的判断，STATUS_CREATE 已经隐含 != PAY

// 超时关单
if (order.getStatus() != STATUS_PAY && order.getStatus() != STATUS_CANCEL) { ... }

// 管理员发货
if (order.getStatus() == STATUS_PAY && !order.isRefund()) { ... }
//                                    ↑ 只有这个入口加了 isRefund 判断

// 管理员退款
if (order.getStatus() == STATUS_PAY || order.getStatus() == STATUS_REFUND) { ... }
```

##### 收口后的样子

```java
// 所有入口，同一个调用模式：
canTransition(order.getStatus(), TARGET_STATUS);          // 或
validateTransition(order.getStatus(), TARGET_STATUS, ...);
```

##### 优劣对照

| 维度 | 散落 if/else | 收口到状态机 |
|------|-------------|------------|
| **规则位置** | 分散在 5+ 个文件里 | 集中在 `transitions` 一处 |
| **规则一致性** | 每个入口的写法不同、严谨度不同 | 同一份白名单，无歧义 |
| **新增状态** | 逐个文件排查，漏改 = bug | 改一行 `transitions.put(...)`，所有入口自动生效 |
| **新增入口** | 需要翻遍所有已有入口，理解各自规则再模仿 | 调 `canTransition` 即可，自动继承全部保护 |
| **终态防护** | 每个入口各写各的"终态不能改"判断，容易遗漏 | 终态不在 Map 里 → `get()` 返回 `null` → 自动拒绝 |
| **代码 review** | 需要理解每个入口的业务语境才能判断 if 条件对不对 | 看 `transitions` 定义即可，入口只审查"目标状态是否正确" |
| **测试** | 每个入口单独覆盖状态组合，N×M 爆炸 | 测白名单矩阵就够了，入口只管自己的逻辑 |

##### 具体对比：加一个「部分退款」

| 散落 if/else | 收口到状态机 |
|-------------|------------|
| 翻 5 个文件 | 改 2 行 `transitions.put` |
| 管理员发货入口忘了加 `!= PARTIAL_REFUND` → 已部分退款的订单可以被发货 | 状态机自动拒绝：`PARTIAL_REFUND` 不在 `PAY` 的白名单里 |
| 退款入口判断是否覆盖了新状态？不确定，得读代码 | `canTransition(REFUND, PARTIAL_REFUND)` 自动生效 |

##### 核心原则

> **规则是数据，不是代码。** 把"CREATED 能转到哪些状态"写成一份数据（`EnumMap`），而不是写成散落在各处的控制流（`if/else`）。数据可以被所有消费者读取，控制流只属于自己的那个方法。

### 支付回调

#### 三个渠道入口差异表

| 维度 | `wxPayNotify` | `aliPayNotify` | `epayPayNotify` |
|------|-------------|---------------|-----------------|
| **支付渠道** | 微信支付 | 支付宝 | 易支付 |
| **数据格式** | XML（`request.getInputStream()`） | URL 参数（`request.getParameter()`） | URL 参数 |
| **验签方式** | SDK 内置（`parseOrderNotifyResult` 自带） | 手动 `rsaCheckV1`（非对称 RSA） | 手动 `EpaySignUtil.sign`（对称 MD5） |

| **返回格式** | XML：`<return_code>SUCCESS</return_code>` | 纯文本：`"success"` | 纯文本：`"success"` |
| **共同核心** | `markOrderPaid(...)` | 同一个方法 | 同一个方法 |

> 三个入口只负责**协议适配**（读参数、验签、格式转换），业务逻辑全部收口到 `markOrderPaid`。

#### markOrderPaid 六步顺序图

```
markOrderPaid(orderSn, payId, totalFee, validateAmount, channel)
    │
    ├─ ① 查订单：orderMapper.selectByOrderSn(orderSn)
    │     order == null → fail("订单不存在")
    │
    ├─ ② 金额校验：isPaymentAmountMismatch(totalFee, order.actualPrice)
    │     金额不对 → fail("支付金额不符合")
    │
    ├─ ③ 幂等判断：OrderUtil.hasPayed(order)         ←────── 必须在状态机前
    │     已是 PAY → success("已处理")                        │
    │                                                        │
    ├─ ④ 状态机校验：canTransition(order.status, PAY)  ←────── 必须在幂等后
    │     false → fail("订单当前状态不可支付")                   │
    │                                                        │
    └─ ⑤ executePaidTransaction() → 开启编程式事务            │
          │                                                  │
          ├─ ⑥ doExecutePaidTransaction()                    │
          │     ├─ UPDATE order SET status=PAY WHERE status=CREATE
          │     ├─ affected=0 → handlePaidUpdateMiss
          │     ├─ INSERT payment_flow(flowKey=channel:payId)
          │     ├─ INSERT order_status_log
          │     └─ handleOrderPaid → outbox 消息
          │
          └─ return success / fail → 渠道收口
```

##### 为什么③幂等必须在④状态机之前

```
假设顺序反过来（④在前）：

第一次回调：canTransition(CREATE, PAY) → true → UPDATE → 订单变 PAY ✅
第二次回调（微信重试）：canTransition(PAY, PAY) → false（白名单里 PAY→PAY 不存在）
                   → fail("订单当前状态不可支付")
                   → 微信收到 fail → 重试 → 永远循环（重试风暴）

③在前：
第一次回调：hasPayed=false → 走状态机 → true → UPDATE ✅
第二次回调：hasPayed=true → success("已处理") → 微信停止重试 ✅
```

#### 二义性处理的两种场景

`handlePaidUpdateMiss` 在 `UPDATE affected=0` 时重新查库，区分两种情况：

| 场景 | 订单当前状态 | 原因 | 返回 |
|------|------------|------|------|
| **情况A：并发重复** | `STATUS_PAY` | 另一个支付回调线程抢先执行成功 | `success("已处理")` — 幂等 |
| **情况B：状态被覆盖** | `CANCEL` / 其他 | 在 canTransition 和 UPDATE 之间被取消/关单 | `fail("更新失败")` — 应该失败 |

```java
handlePaidUpdateMiss(order, channel) {
    Order latestOrder = orderMapper.selectById(order.getId());  // 重新查库，不能用旧对象
    if (latestOrder != null && OrderUtil.hasPayed(latestOrder)) {
        return success("已处理");  // 情况A：自己人抢先了
    }
    return fail("更新失败");         // 情况B：被取消/关单了
}
```

#### flowKey 复合键设计

```java
flowKey = channel.getCode() + ":" + payId
//         "WX:wx_abc123"
//         "ALIPAY:20250120000001"
```

##### 为什么需要 channel 前缀？

微信和支付宝各自独立生成流水号，没有跨渠道的协调机制：

```
微信:   transactionId = "20250120000001"
支付宝: trade_no      = "20250120000001"
                         ← 完全相同的流水号！

不用前缀:
  INSERT flow_key='20250120000001' — 微信成功
  INSERT flow_key='20250120000001' — 支付宝冲突！❌

加前缀:
  INSERT flow_key='WX:20250120000001'      — 微信成功
  INSERT flow_key='ALIPAY:20250120000001'  — 支付宝成功 ✅
```

##### 流水冲突必须回滚订单

```
线程A处理订单#123: payId = "wx_abc"
线程B处理订单#456: payId = "wx_abc"  ← 同一 payId，Bug 或攻击

线程A: UPDATE order#123 SET status=PAY → 成功 ✅
线程B: UPDATE order#456 SET status=PAY → 成功 ✅

线程A: INSERT payment_flow(WX:wx_abc, order=123) → 成功
线程B: INSERT payment_flow(WX:wx_abc, order=456) → 唯一约束冲突 ❌

如果不回滚:
  order#123: status=PAY, payId=wx_abc
  order#456: status=PAY, payId=wx_abc   ← 两单声称付了同一笔钱
  payment_flow: wx_abc → order=123       ← 流水只对应一单
  → 财务对账炸裂：一笔钱买了两件商品

回滚后:
  order#123: status=PAY, payId=wx_abc   ✅
  order#456: status=CREATE               ← 恢复，不会显示"已付款"
  payment_flow: wx_abc → order=123       ✅ 一致
```

| 操作 | 不回滚 | 回滚 |
|------|-------|------|
| **订单#123** | PAY（已付款） | PAY（已付款） |
| **订单#456** | PAY（虚假已付款） | CREATE（待支付） |
| **流水表** | `wx_abc → order#123` | `wx_abc → order#123` |
| **对账** | ❌ 一笔钱对应两单 | ✅ 一致 |

### 后置动作的 Outbox 双面设计

支付成功后有三件事要做：确认普通库存、确认秒杀库存、刷虚拟销量。这三件事不写在支付回调事务里，而是通过 outbox 异步处理。

#### 写入侧（handleOrderPaid）：只写一条消息

[PaymentPostActionSupport.java](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/payment/PaymentPostActionSupport.java#L47-L57)

```java

            .messageKey("ORDER_PAID_POST_ACTION:" + orderId)
            .topic(LocalMessageTopics.ORDER_PAID_POST_ACTION)
            .bizType(BIZ_TYPE_ORDER)
            .bizId(String.valueOf(orderId))

关键特征：
- **只有 `topic`，没有 `exchange`/`routingKey`**——不走 RabbitMQ，走本地 handler
- **与 `markOrderPaid` 在同一事务内写入**——订单变 PAY 和消息写 INIT 同时落库
- **payload 只有 orderId**——零业务数据，全部在执行侧按需查询

#### 执行侧（handle）：订阅自己的 topic，做三件事

#### 双面设计全景

```
                         写入侧                           │              执行侧
─────────────────────────────────────────────────────────┼────────────────────────────────────
                                                          │
  markOrderPaid() 事务内                                   │  outbox relay 独立事务
  ┌─────────────────────────────────────────┐             │  ┌──────────────────────────────────┐
  │                                         │             │  │                                  │
  │  UPDATE order SET status = PAID         │             │  │  1. confirmFrozenStockByOrderId   │
  │  INSERT payment_flow                    │             │  │     └─ inventory_flow 流水幂等     │
  │  INSERT local_message ───────────────┐  │             │  │     └─ goods_product.frozen→0     │
  │         topic=ORDER_PAID_POST_ACTION │  │             │  │                                  │
  │         status=INIT                  │  │             │  │  2. confirmPaidStock              │
  │         exchange=NULL ← 本地handler  │  │             │  │     └─ order_activity_relation    │
  │         routingKey=NULL             │  │             │  │         CAS: FROZEN→CONFIRMED      │
  └─────────────────────────────────────┼──┘             │  │     └─ seckill_sku.frozen - N      │
                                        │                 │  │                                  │
                                        │   同一事务，     │  │  3. updateVirtualSales            │
                                        │   原子提交       │  │     └─ goods.virtual_sales + N     │
                                        │                 │  │     └─ 异常吃掉，不拖累①②           │
                                        ▼                 │  │                                  │
                                   local_message 表       │  │  成 → markSent                    │
                                   （待办凭证）            │  │  败 → markFailed(retryCount+1,    │
                                                          │  │          nextRetryTime=指数退避)   │

```

#### 为什么分成两面

| | 写入侧 | 执行侧 |
|------|--------|--------|
| **在哪个事务** | `markOrderPaid` 的事务 | outbox relay 的独立事务 |
| **做什么** | 写一条"待办" | 干三件"实事" |
| **速度** | 极快（一条 INSERT） | 可能慢（跨服务 RPC） |
| **失败后果** | 事务回滚 → 渠道重推 | markFailed → 退避重试 |
| **回滚影响** | 订单状态也回滚（合理） | 不回滚订单状态（合理，已经 PAY 了） |

### 三类后置动作的容错等级

| 等级 | 动作 | 幂等方案 | 失败后会怎样 | 重试策略 |
|------|------|---------|-------------|---------|
| 🔴 **必须成功** | `confirmFrozenStockByOrderId` | `inventory_flow` 表 `flowKey` 唯一约束 | 库存永久冻着 → 可售库存慢慢耗光 | throw → outbox retryCount+1 → 指数退避 → 5 次后死信 |
| 🔴 **必须成功** | `confirmPaidStock` | `order_activity_relation.status` CAS（FROZEN→CONFIRMED） | 秒杀库存永久冻着 | 同上 |
| 🟡 **丢了也行** | `updateVirtualSales` | `goods.virtual_sales += N`（无幂等控制，重复加也行——展示数据） | 用户少看几件销量数字 | catch 吃掉，不抛异常。不触发 retry，不连累①② |

#### 为什么③可以"丢了也行"

```java
private void updateVirtualSales(Long orderId) {
    try {
        // ... UPDATE goods SET virtual_sales = virtual_sales + N
    } catch (Exception e) {
        log.error("虚拟销量更新失败，orderId={}，不影响库存确认结果", orderId, e);
        // 不抛！断了异常链
    }
}
```

如果③抛异常，handle() 整体失败 → outbox → markFailed → ①②③全部重试。但①②已经成功了（幂等保护的），重试只是浪费资源。③是展示型数据，错了用户无感知，下次有交易时自然会更新。**吃异常不是不在乎③，是不让③拖垮①②。**

### 支付回调 vs 管理员退款：编排顺序对比

同一个系统里，支付和退款的执行顺序完全相反。原因：**谁在等谁**。

```
支付回调（渠道求我）                管理员退款（我求渠道）
─────────────────────────────────  ─────────────────────────────────
渠道推通知给我                       管理员点"退款"
    │                                    │
    ▼                                    ▼
① 先改本地状态                      ① 先调三方退款
   order_status = PAY                   instance.refund(reqVO)
   （渠道在等，必须快）                  （必须先拿到三方结果）
    │                                    │
    ▼                                    ▼
② 响应渠道 "SUCCESS"                ② 再改本地状态
   （渠道停止重推）                      order_status = REFUND_CONFIRM
    │                                   （如实反映三方结果）
    ▼
③ 异步写 outbox
   （库存确认慢慢做）

┌─────────────┬────────────────────┬──────────────────────┐
│             │    支付回调          │     管理员退款         │
├─────────────┼────────────────────┼──────────────────────┤
│ 谁主动      │ 渠道推给我           │ 我调渠道              │
│ 编排顺序    │ 先改本地 → 后做衍生   │ 先调三方 → 后改本地    │
│ 渠道在等吗  │ 是（推通知等响应）    │ 是（调接口等结果）     │
│ 本地状态    │ 先落，渠道放心        │ 后落，如实反映三方结果  │
│ 失败代价    │ 本地状态没落 → 渠道重推 │ 三方成功但落库失败 →   │
│             │ （可恢复）            │ 状态与事实不符 →       │
│             │                      │ 需对账/人工兜底        │
│ 事务边界    │ @Transactional       │ 编程式事务             │
│             │ markOrderPaid()      │ 只包 persistRefundResult│
│ 回滚影响    │ 状态回滚 + 渠道重推    │ 三方已退款不能回滚      │
└─────────────┴────────────────────┴──────────────────────┘
```

#### 核心原则

> **让不可靠的环节先暴露。** 统一规则，两种实现：
>
> - 支付回调：渠道可靠（会重推），本地状态不可靠（可能并发冲突）→ **先把本地状态定下来**
> - 退款：三方不可靠（可能证书过期、余额不足），本地落库可靠 → **先拿到三方结果再落库**

#### 退款"失败也落库"的补偿设计

"先调三方 → 再落库"这种编排下，如果直接把异常抛出让外层回滚，发生了什么：

```java
// 假想的错误写法
executeRefund(order, reqVO, refundMoney);   // 调微信退款 → 失败，抛异常
persistRefundResult(...);                    // 不会执行
// 异常扔给框架 → 事务没开启 → 什么都没落库
// order_status 还是 PAY
// 管理员看到的界面：没有退款记录，没有错误原因
// 钱呢？ 不知道。退了没？ 看不出来。
```

**关键认知：调用三方失败本身就是一种业务结果。**

退款调微信，有两种明确的结果：
- 微信返回"退款成功" → success=true，结果落库
- 微信返回"余额不足" → 这也是一种结果，也必须落库

如果只有第一种落库、第二种抛异常，那就丢失了"为什么退款失败"这个信息。

所以 `executeRefund` 用 catch 把异常转成 `RefundExecution`：

```java
RefundExecution executeRefund(Order order, OrderRefundReqVO reqVO, ...) {
    try {
        instance.refund(reqVO);                              // 调三方
        return new RefundExecution(true, REFUND_CONFIRM,     // 成功结果
                REFUND_SUCCESS, refundMoney, refundReason);
    } catch (Exception e) {
        return new RefundExecution(false, STATUS_REFUND,     // 失败结果
                REFUND_FAIL, ZERO,
                refundReason + " 退款失败：" + e.getMessage());
                //              ↑ 异常信息截断后拼进 refundContent
    }
}
```

**成功和失败走同一条路进入 `persistRefundResult`：**

```
executeRefund 返回 RefundExecution
    │
    ├─ success=true  → persistRefundResult:
    │    order_status = REFUND_CONFIRM（已退款）
    │    refund_amount = 退款金额
    │    refund_content = "管理员确认退款"
    │    restoreStock()（回补库存）
    │
    └─ success=false → persistRefundResult:
         order_status = STATUS_REFUND（退款中，状态不变）
         refund_amount = 0
         refund_content = "管理员确认退款 退款失败：余额不足"
         refund_status = REFUND_FAIL
         // 库存不回补（钱没退，货不能还）
```

**落库的是"退款失败"这个事实，不是异常被吞掉的痕迹消失。** 管理员看到这条记录就知道：刚才点退款确实调了微信，微信说余额不足，没退成。可以充钱后再退。
```

### 对账四维度图

```
                         Order（订单表）
                    实付金额  actualPrice
                    退款金额  refundAmount
                    订单状态  orderStatus
                          ▲
              ┌───────────┼───────────┐
              │           │           │
           orderSn      orderSn     orderSn
              │           │           │
    ┌─────────┴──┐  ┌────┴─────┐  ┌─┴──────────┐
    │ 维度1       │  │ 维度2     │  │ 维度4       │
    │ PaymentFlow│  │ 已支付    │  │ RefundFlow │
    │ (支付流水)  │  │ Order    │  │ (退款流水)  │
    │            │  │          │  │            │
    │ 金额:      │  │ 方向:     │  │ 金额:      │
    │ payAmount  │  │ 订单→流水 │  │ refundAmt  │
    └─────┬──────┘  └──────────┘  └────────────┘
          │
    payId+payChannel
          │
    ┌─────┴──────────┐
    │ 维度3           │
    │ PaymentChannel │
    │ Bill (渠道账单) │
    │                │
    │ 金额:          │
    │ payAmount      │
    └────────────────┘
    

四个数据源以 Order 为中心枢纽，从四方交叉比对：

| 维度 | 方向 | 检查项 | 差异编码 |
|------|------|--------|---------|
| **1** | PaymentFlow → Order | 流水找不到订单 | `FLOW_WITHOUT_ORDER` |
| | | 订单不是已支付状态 | `ORDER_STATUS_MISMATCH` |
| | | 流水金额 ≠ 订单实付金额 | `AMOUNT_MISMATCH` |
| **2** | Order → PaymentFlow | 已支付订单缺少支付流水 | `ORDER_WITHOUT_FLOW` |
| **3** | ChannelBill → PaymentFlow | 渠道账单找不到内部流水 | `CHANNEL_BILL_WITHOUT_FLOW` |
| | | 渠道金额 ≠ 内部流水金额 | `CHANNEL_AMOUNT_MISMATCH` |
| **4** | RefundFlow → Order | 退款流水找不到订单 | `REFUND_FLOW_WITHOUT_ORDER` |
| | | 退款金额 ≠ 订单退款金额 | `REFUND_AMOUNT_MISMATCH` |

#### 双向检查原则：为什么维度 1 和维度 2 必须同时存在

维度 1 以支付流水为主体查订单，维度 2 以已支付订单为主体查流水。两个方向都做，不是因为冗余——是因为查询的时间窗口不同。

```
阶段一: listPaymentFlows(safeQuery)    → WHERE payment_flow.create_time  IN [窗口]
阶段二: listPaidOrders(safeQuery)      → WHERE order.create_time         IN [窗口]
```

| | 阶段一以流水为主体 | 阶段二以订单为主体 |
|---|---|---|
| 时间字段 | `PaymentFlow.createTime` | `Order.createTime` |
| 能发现的差异 | 有流水但订单有问题 | 有已支付订单但流水缺失 |
| 会遗漏的差异 | — | 流水不在窗口内、但订单在窗口内的已支付订单 |

**典型漏检场景**：订单 23:58 创建，支付流水 00:02 才生成。阶段一以 `PaymentFlow.createTime` 过滤窗口 [Jan 2 00:00 ~ Jan 2 23:59]，这条流水被排除；阶段二以 `Order.createTime` 过滤同窗口，这个订单被扫到。此时 `paymentFlowOrderSnSet.contains(orderSn)` 为 false，触发二次精准查询 `findPaymentFlowByOrderSn`（不带时间窗口限制），如果能查到流水则跳过，查不到才标记 `ORDER_WITHOUT_FLOW`。

> **二次查询的意义**：区分"流水在窗口外（正常）"和"流水不存在（异常）"。如果直接把 `!contains` 当异常，跨日凌晨支付的订单会被误报。

#### "发现不修复"的两条理由

与库存对账不同（`InventoryReconciliationService` 带 `repair=true` 自动修 `locked_stock`），支付对账**只记录差异，不自动修复**。两条原因：

**理由一：修复方向不确定**

库存对账的修复方向是明确的——库存流水是账本，`locked_stock` 必须修正为流水推导值。但支付差异没有"谁是对的"：

- `AMOUNT_MISMATCH`：流水 100 元，订单 99 元。谁是错的？可能是订单计算错误，也可能是支付流水记录错误。程序无法决定应该改流水还是改订单。
- `ORDER_WITHOUT_FLOW`：订单显示已支付，但没有流水。是真的没收到钱（需要人工排查渠道），还是流水表被误删了（需要 DBA 介入）？

**理由二：修复操作不可逆**

支付涉及真金白银。自动把一笔订单的状态从 `CREATE` 改成 `PAY`（因为渠道账单说收到了钱），意味着用户可以不付钱就获得已支付状态——这是一个安全漏洞。反之，自动把 `PAY` 改成 `CREATE`（因为找不到流水），等于收钱不认账——用户投诉风险极大。

> **库存对账可以自动修，因为库存数字是可逆的（多扣了可以加回来）。支付状态涉及资金，修复必须由人确认事实后再执行。**

差异的处理路径：定时任务打日志 → `TradeOpsController` 治理接口暴露差异 → 运维人工确认 → 手动修单。

#### 渠道账单维度发现：已落地为空转

验证方法：在项目内搜索 `PaymentChannelBill` 的所有引用，统计写入路径。

**涉及文件（共 6 个）**：

| 文件 | 类型 |
|------|------|
| `PaymentChannelBill.java` | 实体定义 |
| `PaymentChannelBillMapper.java` | Mapper 接口（`extends BaseMapper`，有 `insert` 能力但未被调用） |
| `PaymentReconciliationServiceImpl.java` | 只读——`listChannelBills()` → `channelBillMapper.selectList()` |
| `PaymentReconciliationServiceTest.java` | 测试 Mock |
| `notes/waynboot-domain-api.md` | 文档 |
| `docs/MODULE_REFACTOR_PLAN.md` | 重构计划 |

**证据**：
- 搜索全项目 `channel.*bill.*insert|insert.*channel.*bill` → **零匹配**
- `PaymentChannelBillMapper` 只声明了 `extends BaseMapper<PaymentChannelBill>`，没有自定义 SQL
- 没有任何 Service、Controller、定时任务调用 `channelBillMapper.insert/save`

**同样空缺的还有维度 4**：
- `PaymentRefundFlow` 的引用文件格局完全一致（实体+Mapper 只读+测试+文档），写入路径同样为零
- 搜索 `refundFlow.*insert|refundFlow.*save` → **零匹配**

**结论**：

```
维度1 ✅  维度2 ✅  维度3 ❌  维度4 ❌
```

维度 3 和 4 的读端逻辑完整（批量查询、N+1 避免、差异分类、空值防护），但表里永远没有数据。渠道账单需要调用微信/支付宝的对账文件下载接口才能写入，退款流水需要对接渠道退款回调——学习项目不具备真实商户号，这两块被砍了。

**为什么这很关键**：维度 3（`CHANNEL_BILL_WITHOUT_FLOW`）是对账最值钱的能力——"渠道收到了钱，但我们系统完全不知道"。这种事故在所有兜底手段（用户投诉、手工查后台、回调监控、超时告警）中都是最晚被发现的，而对账是唯一能系统性、T+1 发现它的手段。维度 3 的空转意味着这个能力在当前代码中不存在。

**维度 3 缺席后的兜底手段**：

| 手段 | 发现方式 | 覆盖率 | 时效性 | 致命缺陷 |
|------|---------|--------|--------|---------|
| 用户投诉→客服 | 被动 | 仅投诉用户 | 数小时~数天 | 沉默大多数直接退款走人 |
| 渠道后台手工查 | 人工 | 取决于运维记不记得 | T+1~T+N | 不可规模化，人眼比对易出错 |
| 回调到达率监控 | 半自动 | 只能检测回调丢失 | 实时 | 渠道没发回调就看不到 |
| 订单超时告警 | 自动 | 全量但误报率极高 | 分钟级 | "狼来了"，告警疲劳 |

所有兜底手段的共同缺陷：**被动、不完整、不可规模化**。自动化对账的核心价值不是"发现了差异"，而是"保证了发现所有差异的确定性"。

### Waynboot 秒杀系统

### 一、漏斗九层图

用户点击「立即抢购」后，请求依次穿过九道关卡。万人并发时，绝大部分请求在前五步就被挡掉（不碰库存、不写库），落库完全不在这条同步链路上——这就是"秒杀不能让 MySQL 直面流量"的完整答案。

### 二、漏斗设计原理

#### 为什么分层

每一层都是一道筛子，越往后代价越大：

| 层次 | 代价 | 拦截率（估算） | 说明 |
|------|------|---------------|------|
| ①②③④ | Java 判空 + 查 DB | ~80% | 非法参数、过期活动、超限购——最快筛掉 |
| ⑤ | Redis Lua 令牌桶 | ~15% | 超频用户、总量削峰——保护 Redis 库存 Lua |
| ⑦ | Redis Lua 库存扣减 | ~4% | 真正的竞争——库存不足、重复抢购 |
| ⑧ | MySQL INSERT | ~1% | 同步路径的终点——只写一条 outbox 消息 |

落库完全不在这条同步链路上——⑧ 只是写一条消息。真正的订单创建由 MQ 消费者异步执行（`SeckillOrderCreateSupport`）。

#### 漏斗 vs 直连

```
❌ 不做漏斗：
  10000 并发 → 全部打 MySQL 查限购 → 连接池耗尽 → 雪崩

✅ 九层漏斗：
  10000 并发 → ①②③④ 挡掉 8000
            → ⑤ 挡掉 1500
            → ⑦ 挡掉 450
            → ⑧ 入库 50 条 outbox
  MySQL 只承受 ~50 次写操作，连接池零压力
```

### 三、★ Token 的定位（一个容易被误解的设计）

> **token 是入场券，不是中奖券。**

#### 为什么需要它

强制用户走"浏览详情 → 领 token → 提交"的正常路径。脚本直接打 `/seckill/submit` 接口，会因为没 token 在 ① 就被挡在门外（参数校验失败）；有伪造 token 的，在 ⑦ Lua 里校验 token 时被 `-4` 拒绝。

#### 为什么不给它"资格"语义

如果把 token 设计成"抢到了资格"，那就得在发 token 时扣库存：

1. **发 token 接口变成新热点**：详情页 PV 远大于提交量——大量"看热闹的人"也会触发库存扣减 Lua，Redis 被打穿
2. **领了不提交**：token 60 秒 TTL → 拿到 token 但犹豫/关浏览器的用户，库存被白白锁住 60 秒
3. **脚本攻击成本极低**：批量领 5000 个 token → 锁死 5000 件库存

#### 设计细节

- token 校验在 **Lua 脚本内部**（不是 Java 层单独 check），因为"校验 token + 扣库存 + 标记用户"必须原子
- 60 秒 TTL 限制了"领票到提交"的窗口
- [SeckillTokenSupport.java](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/java/com/wayn/domain/promotion/support/seckill/SeckillTokenSupport.java) 类注释原话："token 只用于拦截绕过详情页的直接提交请求，不承载库存语义；库存和限购仍由 Redis Lua 原子判断"

### 四、★ 两把令牌桶 + 两套幂等

#### 4.1 限流：两把令牌桶（[SeckillRateLimiterSupport](file:///d:/agent-project/mall/waynboot-domain-promotion/src/main/java/com/wayn/domain/promotion/support/seckill/SeckillRateLimiterSupport.java)）

| 桶 | Key | 容量 | 填充速率 | 防谁 |
|----|-----|------|---------|------|
| SKU 级 | `bucket:sku:{activitySkuId}` | 200 | 200/s | 保护系统——总入口削峰 |
| 用户级 | `bucket:user:{activitySkuId}:{userId}` | 3 | 3/s | 防刷——单用户高频 |

两层是 **AND** 关系：SKU 层放行 **且** 用户层放行，才算通过。

令牌桶算法允许突发（桶初始满 200 → 瞬间 200 个请求同时通过），然后按填充速率稳压（200/s）。比固定窗口计数器更平滑。

#### 4.2 幂等：两套限购（`validateUserPurchaseLimit`）

| 防线 | 存储 | TTL | 拦截范围 | 角色 |
|------|------|-----|----------|------|
| `userPurchaseKey` | Redis | 1 小时 | 抢占窗口内的并发/重复提交 | **闸门**——快速挡量 |
| `order_activity_relation` | MySQL | 永久 | Redis key 过期后的再次购买 | **护栏**——终极正确 |

> [SeckillOrderSubmitSupport.java](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/seckill/SeckillOrderSubmitSupport.java) 注释原话："Redis 只拦截当前抢占窗口，数据库关联表负责持久化兜底，防止 Redis Key 过期后重复购买同一活动商品。"

**只用 Redis**：1 小时后 TTL 到期，用户又能买了——漏了。
**只用 DB**：万人并发下每条 SELECT 查关联表，MySQL 连接池瞬间耗尽——崩了。
**两套配合**：Redis 扛 99.9% 的拦截量（1ms/次），漏网之鱼才走 DB（10ms/次），各自承担自己能承受的职责。

#### 4.3 幂等键的设计

`userPurchaseKey` 的键是 `activityId + goodsId + userId`（**不是** `activitySkuId`）：

> `activitySkuId` 可能在后台重建活动商品时变化，活动级重复购买必须按 `activityId + goodsId + userId` 收敛。

这是"幂等键要选业务上不变的身份"的又一个实例——选择不随运营操作变化的业务主键，而不是可能被重建的技术主键。

#### 4.4 两套限购 vs 两套幂等的对比

| | 限流（令牌桶） | 限购（幂等） |
|------|-------------|------------|
| 第一层 | SKU 桶 200/s | Redis userPurchaseKey |
| 第二层 | 用户桶 3/s | MySQL order_activity_relation |
| 共同哲学 | **闸门挡量、护栏保正确** | 闸门挡量、护栏保正确 |
| 差异 | 两层都是 Redis，都管瞬时流量 | 一层 Redis（瞬时）、一层 MySQL（持久） |

### 五、★ 补偿模式：outbox 失败 → 回滚 Redis

#### 代码

```java
Long acquireResult = acquireRedisStock(...);    // ① Redis 抢占成功

try {
    seckillOrderMessageSupport.saveSubmitMessage(...); // ② 写 outbox
    return buildProcessingResult(orderSn, ...);         // ③ 返回"处理中"
} catch (RuntimeException e) {
    releaseEntranceStock(sku, userId, orderSn, number); // ④ 回滚
    throw e;
}
```

#### 为什么不能用事务包住

Redis 不在 MySQL 的事务里——**跨存储没有原子性，只能"先做 A、失败补 A⁻¹"**。

#### 回滚三个操作

```
① 抢占时 Lua 做的三件事          ④ releaseEntranceStock 的逆操作
──────────────────────────      ───────────────────────────────
stockKey:      100 → 99         →  INCRBY +number → 100
userPurchaseKey: SET            →  DEL
resultKey:      SET PROCESSING  →  DEL
```

#### 如果不回滚

库存扣了 1 件，但 outbox 没写入 → MQ 消费者永远收不到消息 → **订单永远不会被创建**。库存从系统里凭空消失，无人知晓。

#### 补偿可能失败吗

**可能。** 回滚是三条独立 Redis 命令，若此时 Redis 抖动：

- `stockKey` INCRBY 失败 → 库存永久泄漏（无 TTL 兜底，不在对账范围）
- `userPurchaseKey` DEL 失败 → 用户 1 小时后可重试（有 TTL 兜底）
- `resultKey` DEL 失败 → 前端拿到过期结果（有 TTL 兜底）

**致命的是 stockKey**——没有 TTL、没有自动对账、preheat() 是覆盖不是补偿。

#### 跨存储补偿的通用姿势

```
先动外部（可补偿的）→ 再落本地（权威的）→ 外部失败必补偿
```

在这个项目里出现过三次：

1. **阶段 4**：ES + Redis 缓存删除（"跨三存储删除"，本地事务管不到 ES）
2. **阶段 7**：支付预占 + finally 释放（"预占 + 释放"）
3. **本次**：Redis 抢占 + outbox 失败回滚（"抢占 + 补偿"）

**话术**："事务能保护的地方用事务，保护不到的地方用补偿。"

### 六、🔬 考古时刻：`getExistingOrderSn` 是三次事故的化石层

#### 代码

```java

#### 三条证据拼出事故全貌

| 证据 | 位置 | 说明 |
|------|------|------|
| ① Lua 脚本警告 | [RedisCache.java:178](file:///d:/agent-project/mall/waynboot-data/waynboot-data-redis/src/main/java/com/wayn/data/redis/manager/RedisCache.java) | `"orderSn 是 RedisTemplate 序列化后的 ARGV，不能再次手工加引号"` |
| ② catch 降级 | [SeckillOrderSubmitSupport.java:206-214](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/seckill/SeckillOrderSubmitSupport.java) | 反序列化失败 → 返回 null → 降级为"请勿重复抢购"（不 500） |
| ③ `log.warn` 而非 `error` | 同上 | 异常是预期内会复发的（老数据还在 Redis 里），不值得惊动告警 |

#### 事故还原

**根因**：[CacheConfig.java](file:///d:/agent-project/mall/waynboot-data/waynboot-data-redis/src/main/java/com/wayn/data/redis/config/CacheConfig.java) 配置了 `GenericFastJsonRedisSerializer`，Java 侧传给 Lua 的 `orderSn` ARGV 已经被 FastJSON 序列化为 JSON 格式（带一层引号）。

**历史 Bug**：旧版 Lua 不知道这一点，手工又加了一层引号：

```lua
-- Bug 版本：orderSn 已被 FastJSON 包过一层引号，这里又加一层
redis.call('set', userKey, '"' .. orderSn .. '"', 'EX', userTtl)
```

**结果**：Redis 存储的字节是 `""TN123""`（两层双引号），FastJSON 读回时无法反序列化为 Java String → `SerializationException` → 500。

**修复**：Lua 注释禁止重复加引号；Java 侧 catch `SerializationException` 兜底历史脏数据。

> 代码里的"防御性容错 + 兼容注释 + 温和的日志级别"，是事故的化石。看到它们，就该意识到"这里曾经出过事，而且脏数据可能还有残留"。读这类代码等于读项目的历史书。

### 七、异步落单：create 的三件事 + 三份库存 + 超时释放

`SeckillOrderCreateSupport.create()` 是 MQ 消费端，把入口抢到的资格变成真正的订单。

#### 7.1 三件事的核心流程

```java
public void create(String orderJson) {
    SeckillOrderSubmitMessage message = parseMessage(orderJson);
    boolean orderCreatedOrExists = false;
    try {
        // ① 事务内落单（订单 + 冻结两套 MySQL 库存 + 关联表）
        orderCreatedOrExists = Boolean.TRUE.equals(
            transactionTemplate.execute(status -> doCreate(message))
        );
        // ② 事务外补发 60 秒延迟关单消息
        seckillOrderMessageSupport.sendUnpaidDelayMessage(message.getOrderSn());
    } catch (RuntimeException e) {
        // ③ 条件回滚：只有订单真的没入库才释放 Redis 入口库存
        if (!orderCreatedOrExists) {
            releaseEntranceStock(message);
            seckillResultSupport.markFailed(message.getOrderSn(), e.getMessage());
        }
        throw e;  // 抛出去让 MQ 重试
    }
}
```

##### ① 事务外补发延迟消息

**为什么不在事务内发？**

如果延迟消息在事务里发送、而事务稍后回滚（比如订单插入成功但关联表写入失败），这条延迟消息已经发出去了、收不回来。60 秒后超时关单逻辑看到一个不存在的订单（或者状态已经是 CANCEL 的订单），最坏情况下偷吃一次库存释放。

**事务外发失败了怎么办？**

抛异常 → MQ 没 ACK → RabbitMQ 重新投递 → `create()` 再次执行 → `doCreate()` 里 `existsOrder()` 返回 `true` → 跳过创建 → 补发延迟消息。

##### ② 重投幂等

```java
private Boolean doCreate(message) {
    if (existsOrder(message.getOrderSn())) {
        seckillResultSupport.markSuccess(orderSn, null);  // 刷新 resultKey
        return true;  // ← 已存在就走人，不重复创建
    }
    // ... 落单逻辑
}
```

MQ 消费者保证至少一次投递，但不保证仅一次。`existsOrder` 就是幂等守卫——订单号是唯一的，第二次进来直接跳过。

**注意**：`existsOrder` 只查了 `order` 表，没查 `order_goods` / `order_activity_relation`。如果订单主表插入成功但明细/关联失败（事务回滚了），`existsOrder` 不会误判——因为事务回滚后订单主表也没了。

##### ③ 条件回滚：`orderCreatedOrExists`

| 失败场景 | `orderCreatedOrExists` | 释放 Redis 库存？ | 理由 |
|----------|----------------------|-------------------|------|
| `doCreate` 事务内抛异常（订单没入库） | `false` | ✅ 释放 | 入口库存占了，但订单没了 → 还回去 |
| `doCreate` 正常返回 `true`，`sendUnpaidDelayMessage` 失败 | `true` | ❌ 不释放 | 订单已经在库里，释放库存 = 超卖 |
| MQ 重投，`existsOrder` 返回 `true` | `true` | ❌ 不释放 | 同上 |

这个 flag 的精妙之处不是值本身，而是**倒向了谁的错误**：订单在 → 不动 Redis（MQL 失败可重试补发），订单不在 → 还 Redis（避免永久泄漏）。

#### 7.2 三份库存对照

秒杀订单涉及三套库存，分别在两个阶段被扣：

```
阶段 A（submit，入口线程）        阶段 B（create 事务，MQ 消费线程）
───────────────────────────     ────────────────────────────────
Redis: wayn:seckill:stock:*     MySQL: seckill_sku
   stockKey ↓                      available_stock ↓
       1                            locked_stock ↑
                                 MySQL: goods_product
                                    stock ↓
                                    locked_stock ↑
```

| # | 存储 | Key/表 | 列 | 扣在哪里 | 作用 |
|---|------|--------|-----|---------|------|
| 1 | Redis | `wayn:seckill:stock:{skuId}` | — | `submit()` Lua（阶段 A） | 入口削峰，快速判库存 |
| 2 | MySQL | `seckill_sku` | `available_stock`, `locked_stock` | `create()` 事务（阶段 B） | 秒杀活动配额，可对账 |
| 3 | MySQL | `goods_product` | `stock`, `locked_stock` | `create()` 事务（阶段 B） | 平台真实库存，所有渠道共享 |

**为什么 Redis 和 MySQL 都要扣？**

Redis 秒杀库存只负责入口"能不能抢"的快速判断（千人并发不能查 MySQL）。MySQL `seckill_sku` 是活动配额的权威记录（可对账、可恢复）。MySQL `goods_product` 是平台的最终库存锚点——秒杀卖出的这件货，既消耗秒杀配额、也消耗平台库存。

**释放对比**：

| 释放场景 | Redis stockKey | MySQL seckill_sku | MySQL goods_product |
|---------|---------------|-------------------|---------------------|
| 入口抢占失败（outbox 写失败） | ✅ 回滚 | ❌ 没扣过 | ❌ 没扣过 |
| 落单事务失败 | ✅ 回滚 | ❌ 事务回滚了 | ❌ 事务回滚了 |
| 60s 超时关单 | ✅ INCRBY | ✅ available↑ locked↓ | ✅ `cancel()` 内部释放 |

#### 7.3 超时释放的 `if (cancelled)`

```java
public void closeUnpaidOrder(String orderSn) {
    OrderActivityRelation relation = orderActivityRelationService.getByOrderSn(orderSn);
    if (relation == null) return;

    boolean cancelled = orderCancellationSupport.cancel(orderSn, STATUS_AUTO_CANCEL);
    if (cancelled) {
        seckillInventoryReleaseSupport.releaseTimeoutStock(relation);
        seckillResultSupport.markClosed(orderSn);
    }
}
```

`cancel()` 内部执行的 SQL：

```sql
UPDATE `order` 
SET order_status = 'AUTO_CANCEL' 
WHERE id = ? AND order_status = 'STATUS_CREATE'
```

`WHERE order_status = 'STATUS_CREATE'` 是关键——它让这条 UPDATE 变成了一个**比较并交换（CAS）操作**。

**并发场景：支付回调 + 超时关单同时到达**：

```
                    order.status = STATUS_CREATE
                           │
              ┌────────────┼────────────┐
              ▼                         ▼
      支付回调（支付宝）         超时关单（60s 延迟消息）
      UPDATE SET PAID          UPDATE SET AUTO_CANCEL
      WHERE status=CREATE      WHERE status=CREATE
              │                         │
              ▼                         ▼
      updated=1 或 0            updated=1 或 0

只有一条 UPDATE 能成功（InnoDB 行锁 + WHERE 条件只匹配一次）
```

| 先到达 | 后到达 | 先到的 updated | 后到的 updated | cancelled | 释放库存？ |
|--------|--------|---------------|---------------|-----------|-----------|
| 支付回调 | 超时关单 | 1 | 0 | `false` | ❌ 已卖出 |
| 超时关单 | 支付回调 | 1 | 0 | `true` | ✅ 已取消 |

`if (cancelled)` 的语义不是"订单是否取消了"，而是"**是不是我取消的**"——只有真正改了数据库状态的那条线程，才有资格做库存储存等副作用。这和阶段 6 支付回调的 `updated == 0` 判断是同一个公式的镜像：

> **条件 UPDATE → 检查影响行数 → 只有 winner 执行副作用。**

1. **秒杀队列与普通队列隔离** — 秒杀活动高峰时不影响普通订单消费
2. **统一消费模板** — [AbstractSingleMessageConsumer](file:///d:/agent-project/mall/waynboot-message/waynboot-message-consumer/src/main/java/com/wayn/message/consumer/support/AbstractSingleMessageConsumer.java) 固化幂等→处理→ack→标记流程，消费者只实现 `handle()`
3. **失败 nack 不重新入队** — `requeue=false`，失败消息交给 DLX，防止一条坏消息堵死队列
4. **延迟消息按 routing key 分流** — 普通订单和秒杀订单用不同 delay queue，各自独立消费

### 二、消息丢了的三段排查法

消息发出去但消费者没收到？按消息走过的三段路径逐段排查：

```
生产者 ──①──▶ Exchange ──②──▶ Queue ──③──▶ 消费者
```

#### 第①段：生产者 → Exchange

| 排查点 | 怎么看 | 正常 | 异常 |
|--------|--------|------|------|
| ConfirmCallback 的 ack | [RabbitTemplateConfig](file:///d:/agent-project/mall/waynboot-message/waynboot-message-core/src/main/java/com/wayn/message/control/config/RabbitTemplateConfig.java) 日志 | `ack=true` | `ack=false` → Exchange 名写错 / 网络不通 / RabbitMQ 挂了 |

**注意**：本项目日志有 bug（见下文），`ack=false` 时也打印"消息发送成功"，排查时要看 `ack({})` 的括号里的值。

#### 第②段：Exchange → Queue

| 排查点 | 怎么看 | 正常 | 异常 |
|--------|--------|------|------|
| ReturnsCallback | 日志里搜 `returnCallback` | **不触发**（成功路由时不回调） | 触发了 → routing key 和 binding key 不匹配 / 队列不存在 |
| RabbitMQ 管理页面 | `Queues` → 看 `Ready` 计数是否增长 | 有增长 | 0 → 消息没进来，回到第①段或检查绑定 |

确认 `mandatory=true` 已开启，否则消息路由失败 RabbitMQ 直接丢弃，连 ReturnsCallback 都不会触发。

#### 第③段：Queue → 消费者

| 排查点 | 怎么看 | 正常 | 异常 |
|--------|--------|------|------|
| 消费者日志 | 搜 `消费者收到消息` | 有日志 | 没有 → 消费者未启动 / `@RabbitListener` 未生效 / 连的不是同一个 vhost |
| Redis 幂等标记 | `redisKeyEnum.getKey(msgId)` | 第一次消费时不存在 | 已存在 → 重复消息被跳过（不是丢，是防重） |
| 异常日志 | 搜 `消费失败` | 无 | 有 → 业务异常，消息已 nack → 进死信或丢弃 |

#### 查完之后还找不到？

```
检查清单：
☐ 生产者和消费者连的是同一个 RabbitMQ vhost 吗？
☐ Exchange / Queue 是否已声明（Spring 启动时 @Bean 是否生效）？
☐ Exchange 类型是否匹配（x-delayed-message 插件是否安装）？
☐ Queue 是 durable 的吗（MQ 重启后队列还在不在）？
☐ 消费者 prefetch 是不是太小导致消息堆积？
```

### 三、延迟消息三方案对比

| 维度 | 延迟插件（本项目） | 死信 + 队列 TTL | 定时扫表 |
|------|-------------------|----------------|----------|
| **原理** | CustomExchange 内部 Mnesia 表暂存，Timer 精准唤醒 | 消息在"棺材队列"里等过期 → 变死信 → 转发到目标队列 | 定时任务扫库，查到期的记录拿出来处理 |
| **配置量** | 1 个 CustomExchange + N 个 Queue | 至少 2 个 Queue + 2 个 Exchange + 绑定 | 只需 1 张表 + 1 个定时任务 |
| **延迟精度** | 毫秒级（Timer 精准） | 毫秒级（但被队头阻塞毁掉） | 秒级（任务间隔） |
| **队头阻塞** | ❌ 不存在 | ⚠️ **严重**：只检查队头 TTL | ❌ 不存在 |
| **可靠性** | 依赖 MQ 持久化 + Mnesia disc_copies | 依赖 MQ 持久化 | **最高**，数据库 ACID 保证 |
| **可审计** | ❌ | ❌ | ✅ 直接查表 |
| **额外依赖** | 须安装插件（云厂商可能不支持） | 原生 | 零依赖 |
| **本项目用法** | 订单超时关单（order_delay_queue） | — | — |

#### 死信+TTL 的队头阻塞详解

```
死信队列 order.delay.queue
┌──────────┬──────────┬──────────┐
│ 队头      │          │ 队尾      │
│ 消息A     │ 消息B    │ 消息C    │
│ TTL=1小时 │ TTL=1分钟 │ TTL=5分钟 │
└──────────┴──────────┴──────────┘

RabbitMQ 只检查队头消息的 TTL！
队头 A 不到期 → B 和 C 永远出不来。

结果：B 实际延迟 60 分钟，C 实际延迟 55 分钟。
```

### 四、死信三条件

消息变成死信被转发到 `dl-topic-exchange` → `dl-queue` 的三种情况：

| 死因 | 触发条件 | 本项目场景 |
|------|---------|-----------|
| **被拒绝** | 消费者 `basic.reject` / `basic.nack`，且 `requeue=false` | [MessageConsumerSupport.nackWithoutRequeue()](file:///d:/agent-project/mall/waynboot-message/waynboot-message-consumer/src/main/java/com/wayn/message/consumer/support/MessageConsumerSupport.java) — 业务处理失败时调用 |
| **过期** | 消息在队列里超过 TTL（`x-message-ttl` 或 `expiration`） | 本项目未使用，但队列可配 |
| **队列满了** | 队列达到最大长度（`x-max-length`），溢出消息变死信 | 本项目未设队列长度限制 |

#### 没有 DLX 时 nack 的消息去哪？

```
requeue=true（默认）：
  消息回到队头 → 再投递 → 再失败 → 再回到队头 → 死循环
  → 堵死队列，后续消息全部堆积 💥  ← 最常见的事故形态

requeue=false 且无 DLX：
  消息被 RabbitMQ 静默丢弃 → 无痕丢失
```

#### 本项目的正确做法

```java
// MessageConsumerSupport.nackWithoutRequeue()
channel.basicNack(deliveryTag, false, false);
//                                    ↑
//                          requeue=false ← 拒绝重新入队，让 DLX 接管
```

- `requeue=false` → 消息不进死循环
- DLX 存在 → 消息转入 `dl-queue`，人工排查

### 五、消费者模板：AbstractSingleMessageConsumer

所有消费者继承此模板类，固化幂等、ack/nack 流程：

```
consume(channel, message)
  │
  ├── resolveMessageId() → 优先取 correlation header，兜底用 messageId
  │
  ├── ackIfConsumed() → Redis 已有消费标记？
  │   ├── 是 → channel.basicAck() + return（重复消息直接跳过）
  │   └── 否 → 继续
  │
  ├── handle(body) → 具体消费者的业务逻辑
  │   ├── 成功 → ackAndMarkConsumed() → ack + Redis 标记
  │   └── 失败 → nackWithoutRequeue() → nack(requeue=false)
  │                                        ↓
  │                                   进入死信队列
```

[MessageConsumerSupport](file:///d:/agent-project/mall/waynboot-message/waynboot-message-consumer/src/main/java/com/wayn/message/consumer/support/MessageConsumerSupport.java) 的幂等 key 优先级：

```
correlation header（生产端回调写入，最稳定）
  → messageId（RabbitMQ 自带）
    → deliveryTag（channel 内稳定，最后兜底）
```

### 七、模板五步 + 三个抽象方法

`AbstractSingleMessageConsumer.consume()` 是一个 `final` 模板方法，把消费流程固化为五个步骤。子类不能覆写它，只能实现三个抽象方法。

#### 五步流程

```
consume(channel, message)                          // final，子类不能改
  │
  ├─ ① 解析消息体 + 幂等 ID
  │     body = bodyAsString(message)
  │     msgId = resolveMessageId(message)
  │
  ├─ ② 幂等检查
  │     ackIfConsumed() → Redis 已有标记？→ 是：ack + return
  │
  ├─ ③ 执行业务
  │     handle(body)  ← 子类唯一要填的代码
  │
  ├─ ④ 成功：ack + 标记
  │     ackAndMarkConsumed() → basicAck + Redis.set
  │
  └─ ⑤ 失败：nack 不进队
        nackWithoutRequeue() → basicNack(requeue=false) → 进死信
```

#### 子类必须实现的三个抽象方法

| 抽象方法 | 作用 | 举例 |
|---------|------|------|
| `handle(body)` | 业务逻辑 | `mobileApi.submitOrder(body)` |
| `consumerName()` | 日志标识 | `return "OrderPayConsumer"` |
| `redisKeyEnum()` | 幂等 key 前缀 | `return ORDER_CONSUMER_MAP` |

#### 模板方法的收益

六个消费者，如果各自手写消费流程：

```java
// ❌ 每个消费者都要复制 20 行
String body = new String(message.getBody(), UTF_8);
String msgId = resolveMsgId(message);
if (redisCache.get(key) != null) { channel.basicAck(); return; }
try { mobileApi.xxx(body); channel.basicAck(); redisCache.set(key, msgId); }
catch (Exception e) { channel.basicNack(tag, false, false); }
```

有模板后：

```java
// ✅ 每个消费者只需实现 3 个方法，handle 里只写 1 行业务代码
@Override protected void handle(String body) { mobileApi.submitOrder(body); }
@Override protected String consumerName() { return "OrderPayConsumer"; }
@Override protected RedisKeyEnum redisKeyEnum() { return ORDER_CONSUMER_MAP; }
```

### 八、ack 顺序的结论修正

#### 项目的注释

`MessageConsumerSupport.ackAndMarkConsumed()` 的注释写道：

> 保持历史顺序：先 ack broker，再写 Redis 幂等标记，避免 ack 失败但 Redis 已标记导致消息丢处理。

#### 驳斥："丢处理"推不出来

标记写的**前提**是 `handle(body)` 已经成功执行完毕。所以：

```
"标记在" = "业务已执行成功"
```

当标记在、ack 失败导致消息重投时，幂等检查命中标记，跳过重投——**这是正确的幂等行为，不是丢处理**。

尝试构造"丢处理"反例，全部失败：

| 尝试 | 结果 |
|------|------|
| ack 成功, Redis.set 抛异常 | 标记没写入，消息已被 broker 删除 → 不丢 |
| ack 成功, JVM 崩溃 | 同上 |
| ack 抛 IOException | 整个方法炸了，标记没写，外层 catch → nack → 进死信 → 不丢 |

**不存在"标记在但业务没做"的窗口，因为标记在的前提就是业务做完了。**

#### 两种顺序的真实差异

| 顺序 | 失败场景 | 真实后果 | 严重程度 |
|------|---------|---------|---------|
| **先 ack 后标记**（当前） | ack 成功，标记写入失败 | 将来同一消息重投会被重复执行业务 | **低**：依赖业务层幂等兜底 |
| **先标记后 ack** | 标记写入成功，ack 失败 | 消息进死信，但业务已执行成功 | **低**：死信误报，人工判断 |

**两种顺序的严重程度相同，没有谁明显优于谁。** 都依赖业务层状态机/唯一约束做最终兜底，Redis 标记只是第一层"去抖"。

#### 结论

注释的理由站不住脚——这是第 5 例"注释 ≠ 现实"：

| # | 文件 | 注释/代码说的 | 实际 |
|---|------|-------------|------|
| 1 | `StatusConverter` | MAN/WOMAN | 实际用数字编码 |
| 2 | `RedisLock` | 单位未标注 | 可能秒/毫秒混淆 |
| 3 | `syncGoods2Es` | 已接线 | 实际未接入调用链 |
| 4 | 库存差量注释 | 夸大风险 | 实际影响范围小 |
| 5 | `ackAndMarkConsumed` | "先 ack 避免丢处理" | 标记在 = 业务已完成，不会丢 |

### 九、"幂等标记只是 60 秒去抖器"——分层认知

#### 标记的生命周期

```java
redisCache.setCacheObject(key, msgId, redisKeyEnum.getExpireSecond());
```

每个消费者的 `RedisKeyEnum` 设了过期时间（通常是 60-120 秒）。**标记不是永久的。**

#### 分层定位

```
消费端 Redis 标记（60 秒 TTL）
  │
  │  作用：去抖（debounce）——防止同一条消息在短时间内被重投后重复处理
  │  覆盖范围：同一 msgId，60 秒内
  │  失效场景：标记过期后重投、标记写入失败
  │
  ▼
业务端状态机/唯一约束（永久）
  │
  │  作用：真正的一致性保障——已支付的订单不会被再次支付
  │  覆盖范围：业务状态，永久
  │  失效场景：——（数据库 ACID 保证）
```

#### 为什么是"去抖"而不是"去重"？

| | 去抖 | 去重 |
|---|------|------|
| 目标 | 消解短期内的重复投递 | 永久不重复 |
| 时效 | 60 秒 TTL | 永久 |
| 实现 | Redis 缓存 | 数据库状态机 |
| 失败后果 | 业务被执行两次 | 数据错乱 |

**Redis 标记是"快速去抖器"，数据库状态机是"真正的去重器"。** 前者的价值在于：在 99.9% 的场景下快速拦截重复投递，避免不必要的业务调用。但它的可靠性不构成正确性的前提——正确性始终落在数据库层面。

### 十、三级降级的问题：没有幂等键比错误的幂等键安全

#### 三级降级回顾

```java
public String resolveMessageId(Message message) {
    // ① correlation header（跨重投稳定）
    String msgId = message.getMessageProperties().getHeader(RETURNED_MESSAGE_CORRELATION_HEADER);

    // ② messageId（跨重投稳定）
    msgId = message.getMessageProperties().getMessageId();

    // ③ deliveryTag（只在当前 channel 内稳定）
    return String.valueOf(message.getMessageProperties().getDeliveryTag());
}
```

#### deliveryTag 为什么不可靠

deliveryTag 是 channel 内的投递序号，不是消息 ID：

```
第一次投递: deliveryTag=5  →  写入 Redis key "consumer:5"
重投:       deliveryTag=8  →  查 Redis key "consumer:8"  →  null  →  误判为新消息

更严重的情况——channel 重连后编号复用：
channel1: deliveryTag=3  →  Redis "consumer:3"  →  channel1 断开
channel2: deliveryTag=3  →  另一条消息  →  查 Redis "consumer:3"  →  命中！→  消息被误判为已消费 → 丢失
```

#### 核心原则：没有幂等键比错误的幂等键安全

| | 没有幂等键 | 错误的幂等键（如 deliveryTag 跨 channel） |
|---|-----------|----------------------------------------|
| 后果 | **重复处理**（false negative） | **丢消息**（false positive） |
| 可接受性 | 依赖业务层状态机兜底，通常可接受 | 消息静默丢失，不可接受 |
| 发现难度 | 业务日志可追踪 | 几乎发现不了 |

在消息系统中，**false positive（误判为已消费 → 丢消息）远比 false negative（漏判 → 重复执行）危害大。** 重复执行可以有业务层兜底，丢消息则完全没有痕迹。

#### deliveryTag 的第三级真实定位

```
第一级 correlation header  →  幂等保障
第二级 messageId           →  幂等保障
第三级 deliveryTag         →  容错保障（保系统不崩，不保幂等正确）
```

降级到第三级时，应该触发告警：

```java
log.warn("消息缺少 messageId 和 correlation header，降级使用 deliveryTag={}，"
       + "幂等将不可靠，请检查生产端配置", deliveryTag);
```

**正确做法：前两级缺一不可，第三级只是让系统在配置错误时不 NPE。**

### 十三、"至少一次 + 幂等 = effectively once" 公式

#### 核心等式

```
at-least-once delivery × idempotent processing = effectively-once semantics
```

#### 拆解

```
MQ / outbox relay 保证：消息至少到达一次（可能重复投递）
                        ↓
消费端幂等保证：同一条消息多次到达只执行一次业务
                        ↓
最终效果：业务语义上只执行了一次（effectively once）
```

#### 本项目的实现

| 层 | 保证什么 | 怎么保证 |
|----|---------|---------|
| 发件箱 + relay | **至少一次** | 数据库事务 → relay CAS 更新 → MQ 持久化 → DLX 死信兜底 |
| 消费端 Redis 标记 | **去抖**（60 秒内） | `ackIfConsumed` 查标记 → 存在即跳过 |
| 业务端状态机 | **去重**（永久） | `UPDATE ... WHERE status='UNPAID'` → rows=0 跳过 |
| 发件箱 messageKey 唯一索引 | **防重复写入** | `DuplicateKeyException` 视为幂等成功 |

#### 它不能保证什么

**不是 exactly-once（精确一次）。** 如果 Redis 标记过期 + 业务状态机恰好允许重复执行（比如 `UPDATE counter SET cnt=cnt+1` 而非 CAS），消息会被执行两次。

**effectively once 的前提是业务层必须做 CAS 更新或唯一约束，不能依赖消费端标记。**

### 十四、端到端幂等键贯通

一条消息从写入到消费，幂等 ID **全程不变**：

```
① saveMessage                ② relay.sendRabbitMessage
messageKey = "ORDER:1001"    messageId = messageKey           = "ORDER:1001"
                              CorrelationData = messageKey    = "ORDER:1001"
                                       │
                                       ▼
                              ③ RabbitMQ 携带
                              correlation_id: "ORDER:1001"
                              message_id: "ORDER:1001"
                                       │
                                       ▼
                              ④ 消费者 resolveMessageId
                              correlation header → "ORDER:1001"  ← 命中！
                              redisKeyEnum.getKey("ORDER:1001") = "order:consumer:ORDER:1001"
```

#### 关键设计

```java
// relay: buildRabbitMessage — messageKey 双重写入
MessageBuilder.withBody(payload)
    .setMessageId(message.getMessageKey())  // ← RabbitMQ 原生 messageId
    .build();

// relay: sendDirectRabbitMessage — messageKey 作为 CorrelationData
rabbitTemplate.convertAndSend(exchange, routingKey, rabbitMessage,
    new CorrelationData(message.getMessageKey()));  // ← 生产者确认回调拿到的
```

```java
// 消费端: resolveMessageId — 优先取 correlation header
String msgId = message.getMessageProperties().getHeader(RETURNED_MESSAGE_CORRELATION_HEADER);
// 退路: messageId（RabbitMQ 原生，同样是 messageKey）
msgId = message.getMessageProperties().getMessageId();
```

**messageKey 从数据库一路贯通到消费端 Redis key，中间没有转换、没有变名。**

### 十五、本地 handler 的第二种用法

发件箱不只是"发 MQ 的保险"，它还是**本地补偿的调度器**。

#### 场景：支付成功后的库存确认

```
支付回调 → 改订单状态 → 确认冻结库存 → 更新虚拟销量
                          ↑
                    如果直接调用，这里挂了怎么办？
                    订单已改 PAID，库存还是冻结的 → 永久泄漏
```

#### 用 outbox 本地 handler

```java
// PaymentPostActionSupport — 实现了 LocalMessageHandler
// ① 事务内写消息（跟订单状态一起提交）
public void handleOrderPaid(Long orderId) {
    localMessageService.saveMessage(LocalMessageCreateCommand.builder()
        .messageKey("ORDER_PAID_POST_ACTION:" + orderId)
        .topic("ORDER_PAID_POST_ACTION")
        // ← 没有 exchangeName / routingKey → 走本地 handler
        .build());
}

// ② relay 扫到后调用
@Override
public void handle(LocalMessage message) {
    Long orderId = parseOrderId(message.getPayload());
    orderStockSupport.confirmFrozenStockByOrderId(orderId);  // 库存确认
    updateVirtualSales(orderId);                              // 虚拟销量
}
```

#### 对比

| | MQ 消息 | 本地 handler 消息 |
|---|--------|-----------------|
| 用途 | 跨服务通知（邮件、关单） | 本进程后置补偿（库存、销量） |
| relay 分发 | `rabbitTemplate.convertAndSend` | `findLocalHandler(topic).handle()` |
| 幂等保障 | 消费端 Redis + 业务 CAS | messageKey 唯一索引 + 业务自身幂等 |
| 重试 | relay markFailed 指数退避 | relay markFailed 指数退避（同一套） |

**同一套 relay、同一套重试、同一套补偿日志——两种消息类型共享全部基础设施，唯一的区别是分发方式不同。**

### 十六、relay 先投递、后标记

// LocalMessageRelaySupport.relaySingleMessage()
private void relaySingleMessage(LocalMessage message) {
    dispatch(message);                            // ① 先投递
    localMessageService.markSent(message.getId()); // ② 后标记
}

#### 当前顺序：先投递、后标记 → 至少一次

正常路径：
  dispatch ✅ → markSent ✅ → status=SENT

崩溃路径（dispatch 成功，markSent 前崩了）：
  dispatch ✅ → 消息已到 MQ → 崩溃！
  markSent ❌ → status 还是 INIT
  下次 relay 扫描 → status=INIT → 又投一次！

语义：至少一次（可能重复，绝不丢失）

#### 先标记、后投递 → 至多一次

正常路径：
  markSent ✅ → dispatch ✅ → status=SENT

崩溃路径（markSent 成功，dispatch 前崩了）：
  markSent ✅ → status=SENT → 崩溃！
  dispatch ❌ → 消息根本没发 → 永久丢失
  数据库写的是 SENT → 运维看表"一切正常" → 实际丢了！

语义：至多一次（可能丢失，绝不重复）

#### 坏结果

"先标记后投递"的灾难在于丢消息没有告警：数据库写的是 SENT，所有监控指标正常，但消息实际上从没到达 MQ。只能在用户投诉"为什么订单没创建"时才发现——而且排查时表里一切正常，根本找不到原因。

#### 为什么选"至少一次
丢一条消息 = 用户付了钱订单没创建 → 投诉 → 对账 → 人工补单
多投一次   = 消费端幂等挡掉 → 用户无感知 → 零成本

### 十七、两个 admin 实例 relay 同时扫到同一条消息，markSent 的 CAS 能防住重复投递吗？

#### 答案

**防不住。** relay 是先发 MQ（`convertAndSend`）再改状态（`markSent`），两个实例的 MQ 投递发生在 CAS 更新之前。

```
admin-1: convertAndSend ✅ → markSent(WHERE status='INIT') ✅
admin-2: convertAndSend ✅ → markSent(WHERE status='INIT') ❌ rows=0
                             ↑ MQ 已经发了两次了，CAS 只能防状态写两次
```

#### 为什么不防

| 如果用 ShedLock | 如果用数据库抢单 |
|---------------|----------------|
| 需要引入 `@SchedulerLock` 依赖 | 需要新增 PROCESSING 状态 + CAS 抢占逻辑 |
| 只有一把锁，同一时刻只有一个实例在扫 | 需要 SELECT FOR UPDATE 或 UPDATE ... LIMIT 50 |
| 另一个实例本轮空转 | 抢到的和不抢到的各处理一批 |
| ⚠️ 如果持锁实例宕机，锁在 TTL 过期前所有实例都停摆 | ✅ 不依赖锁，宕机影响面小 |

#### 真实原因

**消费端已经有两层幂等（Redis 标记 + 业务 CAS），relay 再加抢单是"第三层防线的第三层"，边际收益趋近于零。**

```
MQ 投递本身就是 at-least-once → 消费者天然假设消息可能重复
                               → 去抖 + 去重已就位
                               → relay 双实例只是多了一条"至少一次"的路径
                               → 不值得为它引入 ShedLock 依赖或 PROCESSING 状态
```

### 十八、双轨制延迟

同是 `local_message` 表里的消息，延迟由两套不同的机制承担：

```
local_message
  │
  ├─ 延迟投递（业务需求：下单 15 分钟后关单）
  │    delayMillis = 900000
  │    exchangeName = "order_delay_exchange"
  │    nextRetryTime = NOW          ← 立刻被 relay 扫到
  │    relay 扫到 → sendDelayRabbitMessage → x-delay=900000
  │    "等"在 RabbitMQ 延迟交换机里（Mnesia 表）
  │
  └─ 重试延迟（运维需求：MQ 挂了等 2 秒再试）
       delayMillis = 0
       exchangeName = "order_direct_exchange"
       nextRetryTime = NOW + 2秒    ← relay 2 秒后才扫到
       relay 扫不到 → 等下个周期
       "等"在数据库 nextRetryTime 字段里
```

| | 业务延迟 | 重试延迟 |
|---|---------|---------|
| 目的 | 15 分钟后关单 | MQ 挂了等 2 秒再试 |
| 触发方 | 业务代码设 `delayMillis` | `markFailed` 设 `nextRetryTime` |
| 等待在哪 | RabbitMQ 延迟交换机 | 数据库 `nextRetryTime` |
| relay 行为 | 立刻投给延迟交换机 | 等到点再扫再投 |
| 依赖 | `x-delayed-message` 插件 | 零外部依赖 |
| 精度 | 毫秒级 | 秒级（relay 间隔 5 秒） |

#### 设计评价

**同一张表、同一个 relay，两种等待机制各司其职：**

- 业务延迟借 MQ 的力，精度高，但依赖插件
- 重试延迟留在数据库，零依赖，可靠性最高

没有混在一起——没有把重试延迟也丢给 MQ 延迟交换机（会导致死信+TTL 的队头阻塞），也没有把业务延迟丢给 `nextRetryTime`（15 分钟的延迟精度受 relay 扫描间隔影响）。**各用各的最优路径。**

### 十九、三句话体检

**第一句（发）：** 业务事务里把"要做的事"写进 `local_message` 表，和订单状态一起提交——MQ 挂了、进程崩了都不丢，relay 每 5 秒扫出来投，失败就是指数退避重试，5 次后再失败进 FAILED 等人接管。

**第二句（收）：** 消费端模板把幂等判断、ACK、NACK 全部焊死成 `final` 方法——消费者只写一行 `handle(body)`，永远不会漏写 ACK 或错写幂等 key，失败消息 NACK 不入队直接走 DLX，不堵正常队列。

**第三句（防重）：** 四层防护各管一段——消费端 Redis 标记挡 60 秒内的重投去抖，业务端 `WHERE status='UNPAID'` CAS 挡所有重复执行，发件箱 `messageKey` 唯一索引挡重复写入，补偿日志 + 失败分类让异常可追踪、可度量、可一键重投。

#### 核心公式

```
at-least-once delivery × idempotent processing = effectively-once semantics
─────────────────   ────────────────────────
outbox + relay + MQ    Redis去抖 + 业务CAS + 唯一索引
```

#### 这个项目的真实可靠性层级

```
正确性依赖（绝不能出错）  → 数据库（事务 / 唯一索引 / CAS UPDATE）
协调依赖（不可用时降级）  → Redis（幂等标记过期→重复执行有业务层兜底）
性能依赖（出问题不丢消息）→ RabbitMQ（挂了有 outbox relay 继续重试）
```

#### JWT 内容

```
JWT 结构:
  Header:  { alg: "HMAC256" }
  Payload: { sign: "abc123def456..." }     ← 只放 UUID！
  Signature: HMAC256(payload, secret)

Redis 结构:
  Key:   login:token:abc123def456...
  Value: LoginUserDetail {                 ← 用户详情全在这里
           userId, username,
           deptId, permissions, roles,
           loginTime, expireTime
         }

  Key:   USER_TOKEN_SET:{userId}
  Value: Set<tokenSign>                    ← 用户→会话索引

#### 为什么 JWT 不放用户信息？

| 场景 | JWT 全塞用户信息 | JWT 只放 UUID + Redis |
|------|-----------------|----------------------|
| **踢人下线** | 无法撤销已签发的 JWT | 删 Redis key 即可 |
| **权限即时生效** | 等 JWT 过期（最差 30 分钟） | 清 Redis 会话，下次请求重新加载 |
| **JWT 体积** | 大（权限列表可能很长） | 极小（一个固定长度字符串） |

> 核心原则：**JWT 是离线的身份证，Redis 是实时的通行证。身份证改不了，通行证可以随时吊销。**

### 三、滑动续期

// TokenService.verifyToken()
public void verifyToken(LoginUserDetail loginUser) {

}

### 四、兼容过滤器的「边界归一化」手法

#### 问题

移动端 Sa-Token 配置了 `tokenPrefix=null`（不强制 `Bearer ` 前缀），但前端 HTTP 客户端（axios、Postman）默认会发送 `Authorization: Bearer xxxx`。Sa-Token 会把 `"Bearer xxxx"` 整串当成 token 去 Redis 查，导致匹配失败。

#### 方案：前置 Filter + HttpServletRequestWrapper

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)  // 必须排在所有 Filter 最前面
public class MobileAuthorizationHeaderFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(...) {
        String authorization = request.getHeader("Authorization");
        // 是 "Bearer xxxx" 格式？裁掉前缀
        if (authorization != null && authorization.startsWith("Bearer ")) {
            String token = authorization.substring(7);
            // 用 Wrapper 替换原 request，下游拿到的是裸 token
            filterChain.doFilter(new AuthorizationHeaderRequestWrapper(request, token), response);
            return;
        }
        filterChain.doFilter(request, response);
    }
}
```

#### Wrapper 原理：装饰器模式

```java
private static class AuthorizationHeaderRequestWrapper extends HttpServletRequestWrapper {
    private final String token;

    @Override
    public String getHeader(String name) {
        if ("Authorization".equalsIgnoreCase(name)) {
            return token;  // 拦截，返回裁剪后的值
        }
        return super.getHeader(name);  // 其他 Header 原样透传
    }
}
```

> **为什么不能直接改 Header？** `HttpServletRequest` 是只读接口，没有 `setHeader()`。Wrapper 本质是装饰器模式——不改原对象，用壳拦截 `getHeader()` 返回值。

#### 归一化效果

```
请求:  Authorization: Bearer abc123
       │
       ▼  MobileAuthorizationHeaderFilter
       │  检测到 "Bearer " 前缀 → 裁掉 → 构造 Wrapper
       │  Wrapper.getHeader("Authorization") → "abc123"
       ▼
Sa-Token: 读到 "abc123"（裸 token）→ 正确匹配 ✅
```

#### 为什么必须 `@Order(HIGHEST_PRECEDENCE)`？

```
✅ 正确顺序:
  MobileAuthorizationHeaderFilter (剥离 Bearer)
    → Sa-Token Interceptor (读到裸 token → 正常)

❌ 错误顺序:
  Sa-Token Interceptor (读到 "Bearer abc123" → 查不到 → 401)
    → MobileAuthorizationHeaderFilter (剥离 Bearer)
    → 太晚了，已经 401 返回！
```

### 五、白名单与回调匿名的呼应

#### `/callback/**` 为什么必须匿名？

**回调接口是第三方服务（如微信支付、支付宝）主动调用我们的服务器**，它们不会携带我们的 token：

```
微信支付平台
    │
    │  POST /callback/wxpay/notify
    │  Header: 签名、时间戳……（没有我们的 Authorization！）
    │
    ▼
我们的服务器 → 如果要求鉴权 → 直接 401 → 回调失败 → 订单状态永远不更新！
```

所以 `/callback/**` 必须放行，安全校验由回调接口自己通过签名验证来完成（不在认证框架层面做）。

### Waynboot 交易运营治理体系

> 覆盖四个调度点、配置化设计、两类对账的 repair 差异、六个治理接口及 operator 安全观察点。

### 一、全系统调度点（4 个）

| 调度点 | 所在模块 | 周期 | 干什么 | 锁机制 | 失败策略 |
|--------|---------|------|--------|--------|---------|
| `LocalMessageRelayTask` | `domain-trade` | 5 秒（`fixedDelay`） | 扫描 outbox 中 `PENDING` 消息投递到 MQ | 无锁（幂等可容忍重复） | 状态机重试，超限转 `FAILED` |
| `refreshStockSnapshot` | `admin-api` | 5 分钟（`cron`） | MySQL `goods_product` → Redis 快照预热 | ShedLock `PT4M` | 下次调度重来 |
| `reconcileInventory` | `admin-api` | 每小时（`cron`） | 流水反推 `locked_stock`，可自动修复 | ShedLock `PT30M` | 差异记录 + 修复日志 |
| `reconcilePaymentDaily` | `admin-api` | 每天 02:00（`cron`） | 支付流水 × 渠道账单 × 退款流水 × 订单 四维对账，只发现不修 | ShedLock `PT1H` | 差异 → 治理接口人工处置 |

#### 为什么 `LocalMessageRelayTask` 不用锁？

- `fixedDelay = 5000L`：上次执行完毕后再等 5 秒，不会并发执行。
- MQ 投递天然幂等，即使多实例重复扫到同一条消息，也不影响正确性。
- 其他三个任务涉及"同一时刻只能一个实例跑"（多实例写 Redis 会冲突、大量 SQL 扫全表冲突），用 ShedLock 互斥。

#### ShedLock 参数语义（类注释精华）

| 参数 | 含义 | 设置原则 |
|------|------|---------|
| `name` | 锁名（Redis Key 的业务部分），同 name 互斥 | 不同任务必须用不同 name |
| `lockAtMostFor` | 锁最长持有时间。即使节点崩溃未释放，到期后其他节点可接管 | 略大于任务正常最坏耗时 |
| `lockAtLeastFor` | 锁最短持有时间。防止时钟漂移让两个节点几乎同时运行 | 略大于集群间最大时钟差（`PT30S`~`PT1M`） |

### 二、`TradeScheduleProperties` 的三个设计点

#### 设计点 1：嵌套静态类——"结构即文档"

```java
@ConfigurationProperties(prefix = "wayn.schedule.trade")
public class TradeScheduleProperties {
    private StockSnapshot stockSnapshot;          // 三个任务→三个内部类
    private InventoryReconcile inventoryReconcile;
    private PaymentReconcile paymentReconcile;
}
```

- 每个任务一组参数（cron / limit / bucketCount / repair），互不污染。
- 新人改频率只看这一处，不用翻任务类源码（类注释原话）。
- yml 自动补全路径清晰：

```yaml
wayn.schedule.trade.
  stock-snapshot.cron / .limit / .bucket-count
  inventory-reconcile.cron / .limit / .repair
  payment-reconcile.cron
```

#### 设计点 2：双默认值——"防呆"

```java
// 第一层默认：注解里的 ${...:默认值}
@Scheduled(cron = "${wayn.schedule.trade.stock-snapshot.cron:0 */5 * * * *}")

// 第二层默认：配置类字段里的默认值
public class TradeScheduleProperties {
    private StockSnapshot stockSnapshot = new StockSnapshot();
    public static class StockSnapshot {
        private String cron = "0 */5 * * * *";
        private int limit = 500;
    }
}
```

| 默认层 | 位置 | 什么时候生效 |
|--------|------|-------------|
| 第一层 | `@Scheduled` 注解 | `TradeScheduleProperties` 还没被 Spring 加载到容器时 |
| 第二层 | 配置类字段 | 配置类加载了，但 yml 里没写对应项 |

**注解默认**保证"配置类没来得及生效时也能跑"；**字段默认**保证"配置项缺失时也有值"。冗余但安全——配置系统的"防呆"。

#### 设计点 3：repair 开关——两类对账的核心差异

```java
// 库存对账：有 repair 开关
public static class InventoryReconcile {
    private boolean repair = true;   // 默认自动修
}

// 支付对账：没有 repair 开关
public static class PaymentReconcile {
    private String cron = "0 0 2 * * *";
    // 没有 repair 字段！
}
```

支付对账**根本没有 repair 这个配置项**——不是"不让你修"，而是"这个概念就不该存在"。

### 三、两个对账任务的 repair 差异

| 维度 | `reconcileInventory` | `reconcilePaymentDaily` |
|------|---------------------|------------------------|
| 对账范围 | `inventory_flow` ↔ `goods_product.locked_stock` | 支付流水 ↔ 渠道账单 ↔ 退款流水 ↔ 订单 |
| 能自动修？ | ✅ `repair=true` 自动修正 | ❌ 不修，只报差异 |
| 修复方式 | CAS 条件更新（`WHERE locked_stock = oldValue`） | 无 |
| 差异处理 | 自动写回 + 告警日志 | 差异 → `TradeOpsController` 治理接口人工介入 |
| 锁 | ShedLock `PT30M` | ShedLock `PT1H` |
| operator 来源 | `"scheduler"`（硬编码，标识自动任务） | 无（不写操作） |

#### 两条判据

**判据 1：账本是否完备（能不能算出来？）**

- 库存对账：所有 `locked_stock` 的变化（冻结、释放、确认扣减）都完整记录在 `inventory_flow` 表中，本系统掌握全部账目，流水是完备账本。用流水推导 `locked_stock` 是纯计算（加法减法），不会出错。
- 支付对账：渠道侧账单不在本系统控制范围内。回调可能丢失、渠道可能重复扣款、退款可能有手续费差异。**两边信息不对称**，没有一方掌握"完备的真相"。

**判据 2：以谁为准是计算还是业务判断？（该不该自动改？）**

- 库存对账：`locked_stock` 和流水推导值不一致，一定是 `locked_stock` 写错了。流水是不可变的（insert only），是单一事实来源（Single Source of Truth）。"以流水为准"是**确定的计算结论**，不是判断。
- 支付对账：渠道说扣了 99 元、我们记录说扣了 100 元，谁对？可能是价格计算错、渠道账单延迟、手续费少录、重复扣款……"以谁为准"需要人查日志、联系渠道、看截图——是**业务判断**，不是计算。自动修等于替财务做了决定，修错了就是真金白银的损失。

### 五、operator 安全观察点

#### 当前问题

```java
@PostMapping("local-message/{messageId}/retry")
public R<Boolean> retryFailedLocalMessage(
        @PathVariable Long messageId,
        @RequestParam(defaultValue = "admin") String operator) {  // ⚠️ 客户端传什么就是什么
```

**问题**：`operator` 是 HTTP 请求参数，客户端可以任意伪造。

```
攻击场景：
  张三重投消息，但填 operator=李四
  → 日志："operator=李四"
  → 出事故后追责到李四，张三逃脱
```

#### 为什么审计信息必须来自可信来源？

审计的意义在于"**不可抵赖**"——出事了能追溯到具体操作人。如果 operator 是客户端传的：

- 可以嫁祸同事（填别人的名字）
- 可以伪装系统操作（填 `"scheduler"` 冒充自动任务）
- 审计日志变成废纸——分不清是事故还是嫁祸

#### 改进方向

`operator` 应从 `SecurityContextHolder` 中取当前登录用户：

```java
LoginUserDetail loginUser = (LoginUserDetail) SecurityContextHolder
        .getContext().getAuthentication().getPrincipal();
String operator = loginUser.getUsername();  // 来自 Redis，不可伪造
```

| 来源 | 可信？ | 原因 |
|------|--------|------|
| `@RequestParam` | ❌ | HTTP 请求参数，客户端随意改 |
| `@RequestBody.operator` | ❌ | 同上 |
| `@RequestHeader("X-Operator")` | ❌ | 同上 |
| `SecurityContextHolder.getPrincipal()` | ✅ | 来自 JWT→Redis 链路，客户端改不了 Redis |
| `StpUtil.getLoginId() (Sa-Token)` | ✅ | 同上，服务端会话存储 |

**审计字段的黄金法则：永远不相信客户端传来的任何身份信息。** 客户端说他是谁不重要，服务端知道他是谁才重要。

### 3. 业务测试三写法

以 [PaymentCallbackSupportTest](../waynboot-domain-trade/src/test/java/com/wayn/domain/trade/support/payment/PaymentCallbackSupportTest.java) 为典范：

#### 3.1 契约式命名

方法名本身就是一句完整的业务契约，读出来就是需求：

```java
// ✅ 好：读完方法名就知道测什么、期望什么
wxPayNotifyReturnsSuccessWhenOrderAlreadyProcessed()
wxPayNotifyReturnsFailWhenAmountMismatch()
wxPayNotifyReturnsSuccessWhenConditionalUpdateMissesButLatestOrderAlreadyPaid()
wxPayNotifyReturnsSuccessAndRecordsPostActionWhenOrderUpdated()
wxPayNotifyReturnsFailWhenPaymentFlowConflictsAfterOrderUpdated()
```

命名公式：**`被测方法 + Returns(期望结果) + When(触发条件)`**

#### 3.2 `verify(..., never())` —— 禁止性断言

比"做了什么"更重要的是"绝对不能做什么"：

```java
// 已支付订单收到重复回调 — 绝不能再次更新订单、绝不能重复走后置动作
verify(orderMapper, never()).update(isNull(), any());
verify(paymentPostActionSupport, never()).handleOrderPaid(any());

// 金额不一致 — 校验失败后绝不能更新订单
verify(orderMapper, never()).update(isNull(), any());

// 并发场景下另一个请求已完成状态推进 — 绝不能重复走后置动作
verify(paymentPostActionSupport, never()).handleOrderPaid(any());

// 流水冲突 — 绝不能走后置动作
verify(paymentPostActionSupport, never()).handleOrderPaid(any());
```

`never()` 的价值：它防止的不是"功能做错了"，而是"不该做的做了"——后者往往比前者危害更大，因为副作用（积分、消息、发货）一旦触发，回滚成本极高。

#### 3.3 覆盖异常分支

测试覆盖矩阵中，正常路径只占一行，异常分支占了大半：

| 场景 | 测试方法 | 类型 |
|------|---------|------|
| 订单已支付 + 重复回调 | `wxPayNotifyReturnsSuccessWhenOrderAlreadyProcessed` | 幂等防护 |
| 金额不一致 | `wxPayNotifyReturnsFailWhenAmountMismatch` | 校验失败 |
| 并发：条件更新未命中但最新订单已支付 | `wxPayNotifyReturnsSuccessWhenConditionalUpdateMissesButLatestOrderAlreadyPaid` | 并发竞态 |
| 并发：条件更新未命中且订单仍未支付 | `wxPayNotifyReturnsFailWhenConditionalUpdateMissesAndOrderStillUnpaid` | 并发竞态 |
| 正常推进成功 | `wxPayNotifyReturnsSuccessAndRecordsPostActionWhenOrderUpdated` | 主成功路径 |
| 流水唯一键冲突 | `wxPayNotifyReturnsFailWhenPaymentFlowConflictsAfterOrderUpdated` | 存储冲突 |

六条测试，五条覆盖异常/边界，一条覆盖正常路径——**异常分支的测试价值远高于主成功路径**，因为主路径出问题一眼可见，异常路径出问题要等到生产事故才发现。

### 4. 两个单测基建坑

#### 4.1 MyBatis-Plus Lambda Wrapper 在单测中的元数据缺失

```java
@BeforeAll
static void initTableInfo() {
    MybatisPlusTableInfoTestHelper.init(Order.class);
}
```

**为什么需要它？** 当被测代码中使用 `Wrappers.lambdaUpdate(Order.class).eq(Order::getId, ...)` 这类 Lambda 表达式时，MyBatis-Plus 需要解析 `Order::getId` → 对应的数据库列名。这个映射关系（`TableInfo`）平时由 Spring 启动时自动扫描 `@TableName` 实体生成。

单测不启动 Spring 容器 → `TableInfoHelper` 缓存为空 → `lambdaUpdate` 时抛出缓存缺失异常。

**解决方案**：用测试 Helper 手动初始化：

[MybatisPlusTableInfoTestHelper.java](../waynboot-domain-api/src/main/java/com/wayn/domain/api/common/MybatisPlusTableInfoTestHelper.java)

```java
public static void init(Class<?>... entityClasses) {
    for (Class<?> entityClass : entityClasses) {
        if (TableInfoHelper.getTableInfo(entityClass) == null) {
            TableInfoHelper.initTableInfo(new MapperBuilderAssistant(new MybatisConfiguration(), "test"), entityClass);
        }
    }
}
```

> **记忆锚点**：如果在单测中看到 `MyBatis-Plus` 的 Lambda Wrapper 报错，十有八九是忘了 `initTableInfo`。

#### 4.2 `transactionTemplate = null` 的测试构造器

[PaymentCallbackSupport.java](../waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/payment/PaymentCallbackSupport.java) 同时提供了两个构造器：

| 构造器 | 用途 | `transactionTemplate` |
|--------|------|:---:|
| `@Autowired` 构造器 | Spring 运行时 | 从 `PlatformTransactionManager` 创建 |
| 测试构造器 | 单元测试 | `null` |

```java
// 测试构造器 — 注释直接说明了意图
/**
 * 单元测试构造器。
 */
public PaymentCallbackSupport(EpayConfig epayConfig, AlipayConfig alipayConfig, ...) {
    this(epayConfig, alipayConfig, ..., (TransactionTemplate) null);
}
```

单测里用 `null` 传入事务模板，意味着：
- 每次 `wxPayNotify` 调用中，事务相关代码因 `transactionTemplate == null` 而跳过
- 测试可以直接验证 `orderMapper.update`、`paymentFlowService.savePaidFlow` 的调用行为
- 不需要模拟事务提交/回滚的复杂行为

**这看起来是"对测试妥协"，实际上它是整套单测的基础设施**——没有它，每个测试用例都要构造事务上下文，代码量和复杂度会翻倍。评价一个设计不要孤立地看它"规范不规范"，要放在系统里看它解决了什么问题。

### 5. 测试的能力边界

#### 边界表

| 测试能覆盖 | 测试覆盖不到 |
|-----------|-------------|
| 类内部的逻辑分支（if/else 走对没有） | 跨类的时序（锁 vs 事务提交的先后） |
| 单个方法的输入 → 输出 | 跨模块的装配（方法写了但没人调用） |
| 明确断言的行为 | 配置/部署形态的影响（单机 vs 集群） |
| 单元/行为层面的正确性 | 跨存储的一致性（Redis 成功 + MySQL 失败的组合） |
| Mock 协作方的调用次数与参数 | 真实协作方的副作用（网络超时、序列化兼容性） |

#### 边界之外靠什么补？

| 边界外的问题 | 补充手段 |
|-------------|---------|
| 跨类协作链路 | **集成测试**（`@SpringBootTest`，真实注入 + 真实协作） |
| 装配完整性 | **Spring 上下文加载测试** / 冒烟测试 |
| 分布式并发 | **端到端测试** / 灰度验证 / 生产监控告警 |
| 跨存储一致性 | **契约测试** / 混沌工程（注入存储故障） |
| 配置/部署差异 | **基础设施即代码（IaC）+ 环境一致性检查** |

> **核心原则**：单测是防线的最内层，覆盖范围最小但反馈最快。外层的问题需要外层的手段来补。不存在一招通吃的测试手段，分层防御才是正解。

#### 4.1 `releaseEntranceStock` 回滚失败分析（#16 详细）

**触发场景**：Lua 抢库存成功 → outbox 写失败 → 回滚 `releaseEntranceStock` 时 Redis 网络超时/抖动。

**发生位置**（两个镜像方法）：

| 方法 | 位置 | 触发条件 |
|------|------|----------|
| `SeckillOrderSubmitSupport.releaseEntranceStock()` | submit 入口 | outbox 写入失败 |
| `SeckillOrderCreateSupport.releaseEntranceStock()` | MQ 消费端 | 订单落库失败 |

**回滚的三个操作**：

```
stockKey         ← INCRBY +number   → 把扣掉的库存加回去
userPurchaseKey  ← DEL              → 清除购买标记，允许重试
resultKey        ← DEL              → 清除结果映射
```

若这三条中任何一条失败（特别是 `stockKey`），库存就永久泄漏了。

**命名空间隔离确认**：

| 库存类型 | Key 前缀 | 管理工具 |
|----------|----------|----------|
| 普通 SKU 库存 | `trade:stock:*` | `RedisStockSnapshotSupport` + `InventoryReconciliationService`（定时对账修复） |
| 秒杀活动库存 | `wayn:seckill:*` | **无任何自动化工具覆盖** |

`RedisStockKeySupport` 只用 `trade:stock:*` 前缀，`InventoryReconciliationService` 对账的是 `goods_product.locked_stock`（普通 SKU 表），秒杀的 `seckill_sku.available_stock` 不在其范围内。全文搜索 `seckill.*reconcile` / `reconcile.*seckill` 零匹配。

**唯一的"修复"手段：活动预热 `preheat()`**：

```java
// SeckillActivityServiceImpl.preheat()
redisCache.setCacheObject(stockKey(activitySkuId), sku.getAvailableStock());
```

问题：这是 **SET 覆盖**，不是补偿。它把 Redis 库存强制设为 DB 中的 `availableStock`，但 DB 中的 `availableStock` 已经被成功创建的订单递减过了（见 `freezeSeckillActivityStock` 里的 `available_stock = available_stock - number`）。泄漏的那 1 个库存：
- Redis 里：少了 1（回滚失败没加回去）
- DB 里：也少了 1（正常订单创建时扣了）
- `preheat()` 后：Redis = DB，等于**确认了泄漏**，那 1 个库存永久消失

**结论**：

| 维度 | 判定 |
|------|------|
| 类型 | **缺陷**（窄窗口，但零恢复手段） |
| 实际影响 | 泄漏的库存数 = 少卖的商品数，少卖了但没人知道 |
| 恢复手段 | 无自动修复；`preheat()` 是覆盖不是补偿；活动结束后可人工对账 `seckill_sku` 表的 `available_stock` vs `sold_stock + locked_stock` |
| 修复建议 | ① `preheat()` 改用 `SETNX`（只初始化不覆盖）或加版本号 ② 新增秒杀库存对账定时任务，定期对比 `seckill_sku` DB 库存与 Redis 库存 ③ 或最简单的：`releaseEntranceStock` 失败时记一条告警日志到单独的 error topic |

#### 4.2 支付回调 vs 超时关单竞态（#17 详细）

**触发场景**：用户在秒杀下单后 60 秒内完成微信/支付宝付款，但支付渠道回调到达的瞬间，60 秒超时关单的延迟消息也刚好到达。

**四步追踪**：

```
① markOrderPaid (PaymentCallbackSupport)
   order = findOrderByOrderSn(orderSn)            → status = 101 (STATUS_CREATE)
   hasPayed(order)                                → false ✓（确实是待支付）
   canTransition(STATUS_CREATE, STATUS_PAY)        → true  ✓

② 但超时关单先抢到了行锁：
   closeOrder: UPDATE SET status=AUTO_CANCEL WHERE id=? AND status=CREATE → updated = 1 ✅

③ 支付回调随后执行：
   updateOrderToPaid: UPDATE SET status=PAID WHERE id=? AND status=CREATE → updated = 0 ❌

④ handlePaidUpdateMiss:
   latestOrder = selectById(order.getId())        → status = 103 (STATUS_AUTO_CANCEL)
   hasPayed(latestOrder)                          → false（103 == STATUS_AUTO_CANCEL）
   return fail("更新订单状态失败")
```

**当前处理路径**：

```
seckillOrderMessageSupport.sendUnpaidDelayMessage(orderSn)
       │
       ▼ (60s 后)
closeUnpaidOrder(orderSn)
       │
       ├─ cancel() → closeOrder → UPDATE WHERE status=CREATE → ✅ 赢！
       └─ releaseTimeoutStock() → 释放库存 + 删购买标记
       
                     与此同时...
       
PaymentCallbackSupport.wxPayNotify()
       │
       ├─ markOrderPaid()
       │    ├─ hasPayed(原始 order) → false（101，查的时候还没被关）
       │    ├─ canTransition(101 → 201) → true
       │    ├─ updateOrderToPaid → updated = 0（已被改成 103）
       │    └─ handlePaidUpdateMiss → 二次查询 status=103 → fail
       │
       └─ return "fail"  →  支付渠道认为处理失败 → 重推
                              └─ 重推时：hasPayed? → 103 = AUTO_CANCEL → false
                                 canTransition? → 从 103 不能到 201 → fail
                                 支付渠道持续重推，最终放弃
```

**用户视角的受损**：

```
用户：付款成功，银行扣钱了 ✅
系统：订单已取消，库存已释放 ❌
结果：钱花了，货没有，订单状态是"已取消"
```

**代码判定链**：

| 方法 | 文件 | 行号 | 角色 |
|------|------|------|------|
| `updateOrderToPaid` | [PaymentCallbackSupport.java](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/payment/PaymentCallbackSupport.java) | 371 | CAS UPDATE `WHERE status=CREATE` |
| `handlePaidUpdateMiss` | 同上 | 390 | 二次查询判定 → `fail`（不是 refund） |
| `closeOrder` | [OrderCancellationSupport.java](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/order/OrderCancellationSupport.java) | 135 | CAS UPDATE `WHERE status=CREATE` |
| `closeUnpaidOrder` | [SeckillOrderTimeoutSupport.java](file:///d:/agent-project/mall/waynboot-domain-trade/src/main/java/com/wayn/domain/trade/support/seckill/SeckillOrderTimeoutSupport.java) | 30 | `if (cancelled)` 分支 |

**缩影——两条并发路径的完整对照**：

```
执行顺序          谁赢状态变更      结果
────────────────  ────────────     ──────────────────────────────────────
支付回调先         101 → 201 成功  关单随后到 → updated=0 → cancelled=false
                                    → 不释放库存 ✅ 订单保持已支付

关单先             101 → 103 成功  支付回调随后到 → updated=0 → 二次查询见 103
                                    → fail → 渠道重推 → 最终放弃
                                    → ❌ 钱付了但订单已取消
```

**待验证**：

| 验证项 | 优先级 | 结果 |
|--------|--------|------|
| 是否有自动退款路径（支付渠道重推失败后是否触发退款流程） | **P0** | ✅ **已验证：不存在。** `handlePaidUpdateMiss` 仅返回 `fail`，无任何退款调用；`AdminOrderRefundSupport.refund()` 是管理端手动触发；全文无 `auto.*refund` 或 `cancel.*refund` 的自动链路 |

| `handlePaidUpdateMiss` 是否应该改为主动发起退款而非仅返回 fail | 建议 | ✅ **已确认：当前无任何措施。** 唯一"感知"是用户投诉 |

**对账盲区分析——为什么 `reconcilePaymentDaily()` 发现不了**：

`TradeGovernanceScheduledTask.reconcilePaymentDaily()` 每天 02:00 运行，遍历四个维度：

```

        → 无 PaymentFlow 记录 → 跳过 ❌

维度3：reconcileChannelBills     ← 遍历 payment_channel_bill 表

维度4：reconcileRefundFlows      ← 遍历 payment_refund_flow 表
        → 此场景：从未发起退款
        → 无退款流水 → 跳过 ❌
```

**四个维度全盲**。唯一能发现的方式：外部对照支付渠道账单（需人工登录微信/支付宝商户后台）。

| 当前行为 | 支付回调返回 `fail` → 支付渠道重推 → 重试 N 次后放弃。订单已取消 + 库存已释放 + 用户已付款，三方不一致 |
| 严重程度 | 用户损失真金白银（钱扣了没货），系统无感知 |
| 根因 | `handlePaidUpdateMiss` 仅判"是否已支付"，未判"是否已取消且渠道已扣款"——缺少一个"已取消 + 非待支付"的分支来触发退款/告警 |
